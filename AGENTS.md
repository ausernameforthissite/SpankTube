# AGENTS.md — SpankTube

> Проектная память для Kimi Code. Полный контекст — в `docs/design.md` (дизайн-документ v0.6). Если этого файла нет в репозитории — попроси пользователя добавить его и НЕ выдумывай архитектуру самостоятельно.

## Что это

Самохостируемый прокси YouTube для личного использования. Все обращения к YouTube выполняет только серверная часть; клиенты (React web, Android/Kotlin) работают исключительно с API прокси. Кластер Kubernetes находится за фильтрацией РКН — весь YouTube-трафик идёт через единый SOCKS5-прокси (danted в локальной сети, с авторизацией логин/пароль).

## Стек

- Backend: Java 25 (LTS), Spring Boot 4.x / Spring Framework 7, Gradle (Kotlin DSL), микросервисы в монорепозитории
- Web: React 19 + Vite + TypeScript + Shaka Player
- Android: Kotlin + Jetpack Compose + Media3/ExoPlayer (этап 4)
- Инфраструктура: PostgreSQL (БД на сервис), Redis, RabbitMQ, NFS PVC (RWX) под архив, Kubernetes + ingress с wildcard TLS
- Контракт API: OpenAPI-first, кодогенерация клиентов

## Жёсткие правила (принятые решения — не нарушать без явной команды пользователя)

1. **Egress.** Весь трафик к YouTube/Google — только через `egress-starter` (SOCKS5 с авторизацией, remote DNS в духе `socks5h`). Глобальные JVM-флаги `-DsocksProxyHost` / `-DsocksProxyPort` ЗАПРЕЩЕНЫ: они заворачивают в прокси соединения с БД и брокером. Внутрикластерные соединения (PostgreSQL, Redis, RabbitMQ, межсервисные) — всегда напрямую.
2. **Консистентность egress IP.** Резолв stream-URL и скачивание байтов googlevideo — строго через один и тот же egress: подписанные URL привязаны к IP запросившего. Ключ кэша URL в Redis включает идентификатор egress-режима; при смене режима кэш инвалидируется.
3. **Клиенты не ходят в YouTube.** Никогда и ни при каких условиях: все URL в ответах API ведут на media-service. Это относится и к превью/аватарам. Маршруты web-клиента повторяют YouTube (`/watch?v=`, `/channel/`, `/c/`, `/@`, `/playlist?list=`), но ведут на SpankTube.
4. **Стриминг — DASH для обычных видео и записей трансляций.** По явному решению пользователя HLS разрешён только для активного эфира (раздел 54 design), без перехода других видео на HLS.
5. **Аутентификация.** Свой JWT на Spring Security (BCrypt, RSA-ключи, access 15 мин + refresh с ротацией). Роли: `VIEWER`, `ADMIN`. Keycloak не используем. ACL-проверки личной библиотеки и истории — на сервере. По решению пользователя любой аутентифицированный клиент может воспроизводить и скачивать уже существующую глобальную архивную копию, не добавляя её в свою библиотеку или квоту.
6. **Событийная шина.** Доступ к брокеру — только через собственный интерфейс издателя/подписчика, без сырого RabbitMQ-клиента в бизнес-логике: после стабилизации запланирована миграция на Kafka.
7. **Архив и квоты.** MKV (`bv*+ba` + только созданные людьми субтитры, `ffmpeg -c copy -c:s srt`; автогенерированные не скачивать), сегменты SponsorBlock — главами, `info.json` рядом. Дедупликация активной версии по `video_id`: владельцы через `user_views`, физическое удаление активной версии только после удаления последней ссылки. Версии сохраняются в `video_versions` и не перезаписывают друг друга; в квоту входят все версии с `deleted_at IS NULL`. Квоты: `ADMIN` 50 ГиБ, `VIEWER` 10 ГиБ через env, персональные переопределения админом, LRU при 90% только для активной версии — история по LRU не удаляется, при нехватке места архивация останавливается с ошибкой. Ручное удаление активной версии разрешено. Кнопка «Скачать» — у видео, плейлистов и каналов: персистентная очередь, `ADMIN` приоритетнее `VIEWER`, FIFO внутри роли, случайные задержки между запросами. Обычные save/refresh/download для активного эфира запрещены; отдельная ручная запись эфира разрешена по разделу 56 design.
8. **Upstream.** Весь доступ к YouTube — в youtube-upstream-service за интерфейсом `UpstreamProvider`: NewPipeExtractor (in-process), yt-dlp (sidecar), Data API v3 (только аккаунтные операции, квота 10k ед./день). Поиск видео/каналов через Data API v3 не выполняем. PO-токены — через bgutil-pot-provider. Дизлайки — только Return YouTube Dislike, в API помечать как оценку.
9. **Секреты.** Учётные данные danted, Google OAuth client secret, JWT-ключи, куки — только Kubernetes Secrets / переменные окружения. В коде и репозитории секретов нет.

## Текущий этап: 2 — архив и история

Этап 1 завершён и проверен на реальном видео в Docker: метаданные, DASH через SOCKS5, Range-сегменты и play/pause в Shaka.

Этап 2 реализован и развёрнут в Docker: NFS/MKV, библиотека, ACL, LRU, поиск, превью, очередь с ADMIN-приоритетом и архивный DASH проверены. Автосубтитры отключены. Отдельная приёмка полного MKV со SponsorBlock-главами не завершена; ошибки `429 Too Many Requests` не обходить.

Скоуп финального этапа 2: дата публикации и аватар канала, YouTube-совместимые маршруты, поиск видео/каналов и страницы с превью; `catalog-service` (метаданные, SponsorBlock, RYD, история), `archive-service` (MKV на NFS, пакетные задачи, ACL), PostgreSQL, RabbitMQ через собственный интерфейс, кнопка «Скачать» и библиотека с сортировкой/скачиванием MKV/ручным удалением, квоты и LRU. Подписки и гибридные рекомендации — этап 3, комментарии и Android — НЕ входят в этап 2.

Правила из этапа 1: redirect только на разрешённые YouTube/googlevideo-хосты через тот же egress; DASH для MP4 строится по настоящему `sidx`, искусственные byte-range сегменты запрещены; `play()` вызывается только после завершения `player.load()`.

Дополнение этапа 2 (разделы 22, 24, 27, 29, 31, 33–39 design): только человеческие субтитры; лёгкие превью через `i.ytimg.com` с LRU и fallback; постоянный архив отделён от временных скачиваний на 24 часа; выбор дорожек MKV/MP3; очередь с этапами, байтами и скоростью через SSE; персональные autoplay, скрытие кодеков и лучшее качество; осмысленные имена файлов и локальное время клиента; глобальное переиспользование архива; SSE-журнал подготовки плеера; archive-first, сверка длительности и история версий с квотой всех версий; единые имена файлов с аудиобитрейтом и popup под кнопками со sticky-заголовками; возобновление просмотра и красный прогресс на превью; журнал в панели управления без перезапуска плеера при ротации JWT или пробуждении устройства; перемотка на 10 секунд двойным кликом/тапом по половинам плеера; NewPipe как основной metadata-провайдер с yt-dlp fallback, continuation-token и прямые превью через media-service; таймкоды `t=...s/m...s/h...m...s` в URL с приоритетом над сохранённой позицией; закрытие ошибок кнопкой `×`; вкладки канала, SSE метаданных и короткие токены с пагинацией; одиночный жест открывает собственные controls, театральный режим и временный выбор качества; иерархия библиотеки канал → плейлист/отдельные видео; общий параллельный поиск, меню пользователя, темы, локальные SVG-аватары и регистрация VIEWER по admin-инвайтам.

Дополнение этапа 2 (раздел 40 design): собственный прозрачный player overlay с двумя pill-группами, полной шкалой и официальными цветами SponsorBlock; громкость, субтитры Shaka, autoplay, единое меню качества/аудиодорожки/субтитров (раздел 55), театр и fullscreen; предотвращение выделения и округление позиции при double-tap; одиночное кодирование `categories` в SponsorBlock API; `allSettled` для независимых начальных запросов и ожидание настроек перед запуском Shaka.

Дополнение этапа 2 (раздел 41 design): catalog-service пробрасывает HTTP-статус и JSON upstream-ошибок без подмены на `500`; web распознаёт `ANTIBOT` в Shaka и показывает PO-token/update yt-dlp/adapter actions, включая fallback при пустом состоянии actions.

Дополнение этапа 2 (раздел 42 design): при Docker-деплое синхронизировать весь исходник модуля, а не отдельные файлы; `GET /api/v1/library/locations?scope=global` доступен в актуальном catalog-service и покрыт `LibraryControllerTest`.

Дополнение этапа 2 (раздел 43 design): основной архиватор — `NewPipeDownloader` через `@Primary`; видео/аудио и субтитры скачиваются через media-service Range-запросами без yt-dlp, затем ffmpeg собирает MKV с оригинальными и SponsorBlock-главами, `info.json` и превью. Оригинальные главы берутся из `getStreamSegments`, при их отсутствии — из HTML-описания с таймкодами; ключ кэша `streams:v3`. `MEDIA_SERVICE_URL` обязателен для archive-service. yt-dlp не используется в основном пути архивации; его локальные helpers допустимы только для процессов ffmpeg/ffprobe и удаления файлов.

Дополнение этапа 2 (раздел 44 design): название канала на его архивной странице — ссылка на обычный канал SpankTube. `PlaylistThumbnailService` сохраняет назначенное превью в `playlists/{id}/thumbnail` через media-service; `GET /media/playlist/{id}/archive-thumbnail` отдаёт файл или `404`. API библиотеки возвращает `thumbnailUrl` и `videoIds`; карточки 16:9 показывают сохранённое превью или коллаж 2×2 из превью видео.

Дополнение этапа 2 (раздел 45 design): карточки видео имеют меню `⋮` из пунктов «Добавить в плейлист», «Архивировать», «Скачать». Внутренние плейлисты в `user_playlists`/`user_playlist_items` создаются с произвольным названием, не запускают архивацию при добавлении видео и открываются по `/playlist?list=<UUID>` любому аутентифицированному пользователю; изменять их может только владелец. Для «Видео без плейлиста» используется случайный коллаж 2×2 в общей сетке карточек. При ошибке YouTube во внутреннем плейлисте можно показать метаданные существующей архивной копии только с явным предупреждением и исходной ошибкой/рекомендациями, не скрывая антибот-проблему.

Дополнение этапа 2 (раздел 46 design): при ошибке обычного NewPipe сначала проверять отдельный `KidsVideoClient` на Android Reel через тот же egress, затем yt-dlp. Видео «Детям» определяется машинным `PLAYBACK_MODE_PAUSED_ONLY`, а не локализованным текстом; в API возвращается `madeForKids`. Использовать только прямые HTTPS-форматы без HLS/`signatureCipher`; отсутствие подходящих форматов не маскировать. Объединённая MP4-дорожка с видео и аудио допустима для DASH и архивации без отдельной аудиодорожки.

Дополнение этапа 2 (раздел 47 design): чтение MP4-индекса и начало сегмента используют `MediaRetry` — не более двух повторов только при сетевых ошибках с backoff 1/2 секунды, без повторов HTTP `403/404/429`. Для `sidx` читаются первые 256 КиБ MP4; фактический H.264-профиль берётся из `avcC`, а не предполагается по itag. Если есть только один прогрессивный MP4 без `sidx`, `ProgressiveDashService` скачивает его через egress и с помощью ffmpeg `-c copy` создаёт настоящие DASH-фрагменты в кэше `/tmp/spanktube-dash` на шесть часов; искусственные byte-range сегменты запрещены, один `mdat` не выдаётся как DASH. `VideoDetails.madeForKids` имеет тип `Boolean`, чтобы старые Redis-записи без поля не падали при десериализации; публичный API возвращает для них `madeForKids=false`.

Дополнение этапа 2 (раздел 48 design): архивный MKV не подвергается полному remux перед ответом. `OnDemandDashService` строит `ondemand.mpd` по `CueTime` из Matroska `Cues`, читая `SeekHead` и смещение `SeekPosition=0x53AC`; номер дорожки находится в `CueTrack=0xF7` внутри `CueTrackPositions=0xB7`. `init-v/a.m4s` и `gop-v/a-NNNNN.m4s` создаются через `ffmpeg -c copy` только при фактическом HTTP-запросе и кэшируются; `setts` с `frag_discont` сохраняет абсолютное время GOP в `tfdt`, обнуление `tfdt` запрещено. Полный `ffprobe` допустим только как зарегистрированный fallback при отсутствии Cues. Сформированный MPD проверяется XML-парсером в unit-тесте.

Дополнение этапа 2 (раздел 49 design): egress-проба имеет до двух сетевых повторов; одиночный таймаут не должен сразу отключать Range-запросы. Прогрессивный MP4 скачивается для DASH чанками по 8 МиБ с возобновлением и обрезанием незавершённого чанка; попытка ограничена двумя минутами. Web ждёт MPD такого источника до `player.load()` с видимым журналом и внешним пределом 15 минут; `proxy_read_timeout` для MPD в web nginx согласован с этим пределом. Архивный `MediaClient` повторяет только failed chunk при сетевых сбоях и `502/503/504`, не дублируя байты и не скрывая прочие ошибки. Большой архивный MKV продолжает использовать on-demand DASH из раздела 48.

Дополнение этапа 2 (раздел 50 design): `user_settings.auto_archive=true` по умолчанию, выключатель блокирует только автоматическую архивацию по прогрессу. Дорожки имеют уникальный `trackId`, язык, `original` и `autoGenerated` (NewPipe `isAutoDubbed`); архив всегда выбирает оригинальное аудио и только человеческие субтитры. Выбранные язык и название дорожки записываются в MKV и `info.json` (`audio_track_id`, `audio_language`, `audio_label`). Автоматические дорожки доступны для просмотра после оригинальных/человеческих. MPD использует уникальные Representation id и `Role=main/dub`; плеер выбирает аудио/субтитры без сброса качества или языка. Архивные `subtitle-N.vtt` создаются лениво. Catalog работает от UID 10001 для удаления NFS. Действия библиотеки — иконки, на мобильном — меню `⋮` с MKV/удалением.

Дополнение этапа 2 (раздел 51 design): batch-архивация сначала вызывает `/api/v1/archive/estimate`, собирает все страницы видео/плейлистов и считает новые байты в пуле из четырёх задач, исключая существующие копии. Средняя скорость хранится in-memory через `LongAdder`. `/save` требует действительный `estimateId` после подтверждения пользователем; отмена не создаёт задач. Мобильный ползунок громкости скрыт, громкость 100% регулируется ОС.

Дополнение этапа 2 (раздел 52 design): каналы имеют вкладку «Трансляции» из NewPipe `ChannelTabs.LIVESTREAMS`; записи `POST_LIVE_STREAM` доступны для просмотра, MKV-скачивания и архивации через прежний NewPipe-путь и входят в batch-оценку вместе со всеми страницами `/streams`. На вкладке трансляций значки «В эфире» и «Запись эфира» показываются поверх превью только для соответствующего типа. Активный эфир использует DASH, если доступен, иначе HLS по разделу 54; все медиа-URL ведут на media-service. Обычные save/refresh/download для активного эфира запрещены; отдельная ручная запись разрешена по разделу 56, её прогресс не запускает автоархивацию. Механика больших архивных MKV по GOP не меняется.

Дополнение этапа 2 (раздел 53 design): описания видео разбирает `VideoDescription` через allowlist DOM-тегов без `dangerouslySetInnerHTML`: `<br>` — переносы, `<a>` — ссылки с проверкой схемы. YouTube watch/channel/playlist/shorts/youtu.be/redirect преобразуются во внутренние маршруты SpankTube, внешние HTTP(S) открываются в новой вкладке с `noopener noreferrer`; `javascript:` и прочие схемы не создают ссылок. HTML-сущности декодируются, текст остаётся экранированным React.

Дополнение этапа 2 (раздел 54 design): по явному разрешению пользователя HLS поддерживается только для активного эфира. Upstream сохраняет `liveHlsUrl` наряду с DASH, включая fallback через VisionOS; `/live.m3u8` возвращается публичному клиенту, когда DASH отсутствует. `LiveHlsService` рекурсивно переписывает variant/audio playlists, сегменты, `EXT-X-KEY` и `EXT-X-MAP` через тот же egress, буфер MPD/M3U8 — 8 МиБ. `TYPE=AUDIO` передаётся как `kind=audio`: YouTube-аудио `233`/`234` с исходным `seg.ts` фактически raw AAC с ID3, поэтому proxy выдаёт `.aac`/`audio/aac`; видео — `.ts`/`video/mp2t`. Обычные видео и записи остаются на DASH, обычные save/refresh/download для активного эфира запрещены; ручная запись разрешена по разделу 56. Антибот при получении метаданных не маскируется. Последующая регрессионная проверка подтвердила production-воспроизведение обычных, Kids, архивных, записанных и активных трансляций, включая `rFZHOHl-L8A` с `segment.ts` и `segment.aac`.

Дополнение этапа 2 (раздел 55 design): качество, аудиодорожка и субтитры собраны в `PlayerSettingsMenu` под одной шестерёнкой, с текущими значениями и подменю с возвратом. Меню закрывается при выборе, по Escape и клику вне его; высота ограничена размером видео, список прокручивается. `onInteraction` controls отменяет отложенный таймер скрытия, `touch-action: manipulation` включён; capture не блокирует обработчики кнопок. Мобильная громкость остаётся на уровне ОС.

Дополнение этапа 2 (раздел 56 design): для активного эфира отдельная ручная запись в MKV разрешена; обычные save/refresh/download остаются запрещены. `POST /recording/start` создаёт одну активную запись на пользователя и видео в качестве фактически активного варианта Shaka (`height`/`bandwidth`), без подмены на другое; `/stop` завершает ffmpeg через `q`, `GET /recording` восстанавливает состояние после перезагрузки. Уход со страницы отправляет `keepalive`-остановку, а heartbeat прекращает запись после 45 секунд без открытой страницы. Worker использует только media-service, основную аудиодорожку, соблюдает квоту и публикует `video.archived` как отдельную версию `LIVE_RECORDING`. Имя MKV включает UTC-время начала записи. Кнопка показывает красный круг либо квадрат `currentColor`; после завершения доступно скачивание записи. Авто-refresh и автоархивация live не выполняются. После успешной сборки и проверки MKV `NewPipeDownloader` удаляет только известные временные дорожки/субтитры/`chapters.ffmeta`; итоговый MKV, `info.json` и превью сохраняются, при ошибке исходники не удаляются.

Дополнение этапа 2 (раздел 57 design): в `PlayerSettingsMenu` между субтитрами и качеством добавлена «Скорость воспроизведения» с вариантами 0,25/0,5/0,75/Обычная/1,25/1,5/1,75/2. Выбор задаёт `playbackRate` и `defaultPlaybackRate` у `<video>`, не перезапускает Shaka и сохраняется в состоянии App при переходах между видео внутри SPA; после полной перезагрузки возвращается `1`. На экранах до 640px варианты скорости показываются компактной сеткой 2×4 без длинной вертикальной прокрутки; десктопный список не изменён. Backend, OpenAPI и пользовательские настройки в БД не изменяются.

Дополнение этапа 2 (раздел 58 design): `AppHeader` использует кнопку-лупу с `aria-label`/`title` «Найти» вместо текстовой надписи. Поле, область поиска и кнопка объединены в один скруглённый контейнер с нулевым gap и тонкими разделителями; отдельных рамок у дочерних элементов нет. На экранах до 640px строка не переносится: input гибкий, select до 132px, кнопка 44px; сохранены светлая/тёмная темы и `focus-within`.

Дополнение этапа 2 (раздел 59 design): пустой архивный плейлист после удаления всех видео не должен приводить библиотеку к `500`. В `CatalogRepository.playlists` SQL использует `coalesce(array_agg(...) filter (where video_id is not null), '{}')`, а маппер дополнительно отбрасывает null-ID. `List.of` больше не получает `[NULL]` от `LEFT JOIN`; пустые плейлисты и их thumbnails сохраняются. Регрессия покрыта `CatalogRepositoryTest`.

Дополнение этапа 2 (раздел 60 design): web nginx не должен бесконечно использовать IP старого gateway после его пересоздания. В `web/nginx.conf` заданы `resolver 127.0.0.11 valid=5s ipv6=off` и `$gateway`, поэтому `proxy_pass` заново разрешает hostname через Docker DNS каждые 5 секунд. `Host`, `proxy_read_timeout=900s` для MPD и streaming/SSE-настройки сохранены. Это устраняет постоянные `502 Connection refused` от stale upstream IP.

Дополнение этапа 2 (раздел 61 design): предварительная оценка архивации имеет прогресс. `POST /api/v1/archive/estimate` принимает необязательный client `estimateId`; `GET /api/v1/archive/estimate/{estimateId}` доступен только владельцу. Прогресс хранится in-memory 15 минут и обновляется атомарно по завершении каждого видео. Первоначальный polling раз в секунду заменён SSE и отменой по разделу 63. `newEstimateId()` использует `crypto.randomUUID()` при наличии и `crypto.getRandomValues` как fallback для HTTP по локальному IP.

Дополнение этапа 2 (раздел 62 design): под кнопкой «Архивировать канал» показывается `ChannelArchiveStatus` из `GET /api/v1/archive/channel-status/{channelId}`. `ArchiveRepository.lastChannelArchive` возвращает `max(coalesce(finished_at, created_at))` последней CHANNEL-задачи владельца, даже если файлы удалены. Новые видео — публикации позже этой даты, которых нет в архиве; активный эфир и записи без даты не считаются. Плейлисты — отсутствующие у пользователя в библиотеке, потому что YouTube не отдаёт дату их создания, и это явно указано в UI/документации. Web выводит дату в локальном часовом поясе мелким шрифтом и скрывает её, если архивации не было.

Дополнение этапа 2 (раздел 63 design): `GET /api/v1/archive/estimate/{estimateId}/events` доступен только владельцу и отправляет SSE `page`, `video`, `progress` и терминальные события с числом проанализированных видео, текущей страницей, остатком на ней и скоростью анализа. `DELETE` или обрыв SSE до терминального события переводит активную оценку в `CANCELLED`, прерывает рабочие потоки и не запускает анализ оставшихся в очереди видео; отменённый `estimateId` нельзя подтвердить для архивации. Web использует SSE без polling, останавливает оценку при закрытии диалога, `beforeunload`, `pagehide` и SPA-навигации; на выгрузке страницы применяется `keepalive`. Сетевой abort POST не очищает ID активной серверной оценки до явного результата или отмены.

Дополнение этапа 2 (раздел 64 design): загрузка каналов и видео оптимизирована по модели LibreTube. Вкладка плейлистов запрашивается только через `includePlaylists=true`; метаданные кэшируются в Redis на 5 минут с coalescing одновременных запросов, `streams:v3` сохраняет прежние TTL. `BgutilPoTokenProvider` подключён к NewPipe Web client и передаёт `content_binding=videoId`, visitor data и тот же SOCKS5 во внутренний `bgutil-pot-provider:2.0.2`; yt-dlp получает одноимённый plugin той же версии. После `ApplicationReadyEvent` visitor data и token minter прогреваются асинхронно, не блокируя старт. `ResilientUpstreamProvider` преобразует NewPipe continuation в числовой offset yt-dlp на 30 минут, а при неизвестном токене показывает исходную ошибку; transient `ANTIBOT` и временный сбой страницы получают один повтор NewPipe перед остальными fallback. `spring.mvc.async.request-timeout` и gateway/nginx response timeout для POST-оценки согласованы на 15 минут. Страницы плейлистов канала собираются параллельно с сохранением итогового порядка. Archive preflight пробрасывает runtime-причину `CompletionException` без замены на `Internal archive error`. `spring.mvc.async.request-timeout` увеличен до 15 минут (`ARCHIVE_ASYNC_TIMEOUT_MS`), чтобы длинная оценка не обрывалась стандартными 30 секундами Spring MVC.

Дополнение этапа 2 (раздел 65 design): экспериментальный HTTP/2 отклонён из-за замедления каждого сегмента, сохранён HTTP/1.1-пул. Плеер запускает authenticated fetch манифеста параллельно с метаданными и вызывает `player.load()` только после готовности MPD, включая progressive remux; HLS-only эфир перезапускает подготовку при смене `manifestPath`. Сессия JWT перенесена из `sessionStorage` в `localStorage` с миграцией и событием `storage` для синхронизации вкладок. Refresh-ротация защищена Web Locks API, а при его недоступности — lease в `localStorage` с повторным чтением свежей сессии. «Плейлисты» и «Библиотека» в `UserMenu` — обычные `a[href]`, поэтому middle-click открывает их в фоновой вкладке с той же сессией.

Дополнение этапа 2 (раздел 66 design): превью каналов/плейлистов/библиотеки используют общий `LazyThumbnail`. Первые четыре изображения загружаются eager/high priority, остальные получают `src` через IntersectionObserver в 200px от viewport и декодируются асинхронно. Нативный `loading=lazy` остаётся fallback. Backend превью не меняется: media-service, LRU 32 МиБ, дневной HTTP-кэш и coalescing сохранены.

Дополнение этапа 2 (раздел 67 design): `Mp4IndexService` по умолчанию выбирает одно видео на разрешение с предпочтением MP4 и одно аудио на уникальную подпись `(mimeType, language, label, original, autoGenerated)`, сохраняя все различные дорожки и progressive MP4. `full=true` отключает compact-режим. Обогащённые индексы кэшируются на 5 минут и coalescing защищает повторные MPD. Параллелизм чтения — 6. Модель LibreTube: один `StreamInfo`, затем выбранный media source вместо индексации всех форматов заранее.

Дополнение этапа 2 (раздел 68 design): `CatalogVideoController` получает YouTube-метаданные, SponsorBlock и RYD параллельно через `Mono.zip` на `boundedElastic`, как async dislikes у LibreTube. Тип ответа и обработка ошибок не изменены. `spring.mvc.async.request-timeout` и nginx metadata timeout равны 120 секундам, чтобы reactive контроллер не обрывался на 30/60 секундах. `CatalogVideoControllerTest` подтверждает одновременный старт SponsorBlock и RYD. При регрессии отдельно проверять фактические `sponsorBlock` и `dislikeCountEstimate`, а не только воспроизведение.

Дополнение этапа 2 (раздел 69 design): не удерживать отдельный SSE очереди в каждой вкладке: три вкладки с очередью и логами исчерпывали шесть HTTP/1.1-соединений Chrome/Vivaldi и не позволяли отправить следующий запрос. `useQueue` выбирает одного лидера через Web Locks и рассылает снимки по `BroadcastChannel`; скрытые вкладки отменяют SSE, `metadata/logs` открывается только во время загрузки метаданных. API очереди, проигрывание и архивный Range-стриминг не изменены.

Дополнение этапа 2 (раздел 70 design): googlevideo может ответить `302 Connection: close` на другой хост и вызвать новый TLS handshake на каждый Range. `MediaRedirectCache` переиспользует конечный успешный URL через прежний egress (TTL 30 минут, до 256 записей, проверка хостов и инвалидация по HTTP-ошибке), не скрывая ошибки и не записывая подписанные URL в логи. Метрики пула включены с URI-тегом `/`. При лучшем качестве сначала запускается готовый вариант, затем выбирается лучший с `clearBuffer=false`; полный MPD и меню сохраняются. Не возвращаться к принудительному `play()` после буфера лучшего качества и не повторять redirect исходного URL при наличии действующего кэша. Регрессия — 22 страницы, HLS, архивный Range, RYD/SponsorBlock.

## Окружение

- Параметры danted (IP, порт, логин, пароль) — у пользователя; брать из env/локального конфига, не коммитить.
- Кластер: локальный Kubernetes, ingress с wildcard-сертификатом уже настроен; NFS-шара для архива существует.
- Если YouTube отвечает антибот-ошибкой — не маскировать её костылями: показать ошибку пользователю и предложить варианты (PO-token provider, обновление yt-dlp, смена адаптера).

## Команды

- Сборка: `./gradlew build`
- Тесты модуля: `./gradlew :backend:<module>:test`
- Web: `cd web && npm run dev`
- Web build: `npm run build --prefix web`
- OpenAPI client: `npx openapi-typescript docs/openapi/stage2.yaml -o web/src/api/schema.ts`
- Docker Compose: `docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build`
- После каждого Docker-деплоя: проверить dangling-образы `docker image ls --filter dangling=true` и удалить их `docker image prune -f`. При нехватке диска проверить `df -h /` и `docker system df`; при подтверждённой нехватке места разрешено очистить неиспользуемый Build Cache `docker builder prune -f` без отдельного запроса пользователя, затем проверить итоговый `df -h /`. Контейнеры, образы работающих сервисов, тома и NFS не затрагивать. После очистки не использовать offline-сборку, пока кэш зависимостей не восстановлен обычной сборкой.
- Offline-сборка при подготовленном BuildKit cache: `GRADLE_EXTRA_ARGS=--offline docker compose --env-file deploy/.env -f deploy/docker-compose.yml build`
