# Медиа и воспроизведение

> Тематический справочник по части приложения. Исходные разделы: 8, 20, 24, 33, 34, 40, 47, 48, 52, 54, 67, 70, 71, 73, 75, 76.

## 8. Стриминг медиа

- media-service генерирует **свой DASH-манифест** `/media/v/{videoId}/manifest.mpd` из списка форматов upstream'а: все качества, аудиодорожки, субтитры. URL сегментов указывают на прокси.
- Проброс **Range-заголовков** к googlevideo (перемотка), keep-alive/HTTP2-пул соединений — через egress HTTP-клиент (раздел 7).
- Горячий LRU-кэш сегментов на локальном SSD пода (emptyDir с лимитом): повторный зритель не дёргает YouTube (и не грузит danted).
- Архивное видео стримится с NFS через **ffmpeg remux на лету** (`-c copy`, без перекодирования) в fMP4/DASH — браузеры MKV нативно не играют; ExoPlayer на Android умеет MKV сам.
- **Решение: DASH для обычных видео и записей трансляций**. По явному решению пользователя 2026-11-09 HLS разрешён только для активного эфира (раздел 54).
- Оценка нагрузки: 1080p ≈ 5 Мбит/с на зрителя; медиатрафик выносим на отдельный ingress-хост.

## 20. Итоги этапа 1 и правила для следующих этапов

Этап 1 развёрнут и проверен в Docker на тестовой VM: `upstream_egress_ok=1`, метаданные реального видео, DASH-манифест только с URL media-service, `206 Partial Content` для реального googlevideo и воспроизведение play/pause в Shaka. Секреты находятся только в runtime env с правами `600` и исключены из Docker context.

Зафиксированные практические правила:

- Redirect googlevideo выполняется только через тот же egress и только на HTTPS-хосты `youtube.com`/`googlevideo.com` с поддоменами.
- Для MP4 `initRange` и `indexRange` вычисляются по настоящему `sidx` из контейнера. Искусственное разбиение файла на независимые DASH-сегменты запрещено: оно приводит к `MEDIA_SOURCE_OPERATION_FAILED`. Для форматов без индекса допустим только single-file fallback, без выдачи произвольных кусков за полноценные медиасегменты.
- `play()` и native controls доступны только после успешного `player.load()`. Таймауты manifest/streaming настраиваются отдельно (`timeout`, `connectionTimeout`, `stallTimeout`).
- Docker Compose — поддерживаемое окружение для интеграционных проверок; Kubernetes остаётся целевым production-окружением. BuildKit cache используется для Gradle, при подготовленном кэше допускается `GRADLE_EXTRA_ARGS=--offline`.
- Для WebM и архивного remux нельзя повторять искусственное разбиение MP4: нужен корректный индекс/сегментация либо single-file режим.

План и критерии приёмки финального этапа 2:

1. `youtube-upstream-service`: дата публикации, канал и аватар, поиск видео/каналов/плейлистов с пагинацией, метаданные каналов и плейлистов. Data API v3 для поиска не используется.
2. `media-service`: превью и аватары через egress, корректный DASH по `sidx`, отдача архивного MKV на устройство и для воспроизведения.
3. `archive-service`: `bv*+ba` и созданные людьми субтитры, MKV с `ffmpeg -c copy -c:s srt`, главы SponsorBlock, `info.json`, NFS RWX, персистентная очередь с `ADMIN`-приоритетом, FIFO, jitter и rate limiting, дедупликация задач и файлов.
4. `catalog-service` и `user-service`: PostgreSQL, метаданные, SponsorBlock, RYD-оценка, `videos`/`user_views`, действующие квоты и admin-переопределения, серверные ACL и LRU при 90% с удалением физического файла только после последней ссылки.
5. События `watch.progress`, `video.archive.requested`, `video.archived` / `video.archive.failed` — через собственный event-bus. Автотриггер — 30 секунд или 5% просмотра.
6. Web: дата публикации и ссылка на канал, YouTube-маршруты, поиск и превью, автопропуск SponsorBlock, кнопка «Скачать» у всех сущностей, очередь/прогресс, библиотека по каналам с длительностью/размером/сортировкой, скачивание MKV и ручное удаление, admin-выборки и квоты.
7. Приёмка на реальном видео: MKV и `info.json` на NFS; повторное сохранение не создаёт второй файл или задачу; два пользователя делят файл, но каждый учитывает его размер в квоте; ручное/LRU-удаление ссылки не затрагивает другого владельца, последняя ссылка удаляет файл; зритель видит только своё, администратор — всё; архивное видео играется через DASH; ошибки yt-dlp, очереди и NFS видны пользователю.

## 24. Ревизия очереди, общего архива и загрузки плеера

- Неуспешные задания скрываются через час после `finished_at`. Любое терминальное задание можно скрыть через `DELETE /api/v1/archive/jobs/{jobId}`; `archive_job_dismissals` делает скрытие персональным и не удаляет историю или файл. Активное задание скрыть нельзя.
- `archive_jobs.updated_at` обновляется запросами репозитория при каждом изменении состояния или прогресса. Web показывает локальное время, а для другого дня — дату и время. Название ведёт на `/watch?v=...` внутри SpankTube; переход из popup не закрывает его. Список в popup получает отступ под крестиком.
- Одиночное задание считает элементами этапы `METADATA`, `DOWNLOADING_VIDEO`, `DOWNLOADING_AUDIO`, `SUBTITLES`, `SPONSORBLOCK`, `MUXING`, `CHAPTERS`, `FINISHING`; отключённые опцией этапы не входят в `totalCount`. Байтовый прогресс относится к текущей дорожке и скрывается в терминальном состоянии. Разрешение, кодеки и размер остаются видны после завершения. Плейлисты и каналы разворачиваются в отдельные `VIDEO`-задания.
- Завершающий MKV-remux сохраняет главы SponsorBlock. Для архивных и временных файлов применяется `yt-dlp --mtime`; после ffmpeg файловая дата изменения восстанавливается по `publishedAt`, а в поддерживаемые контейнеры записывается `creation_time`. По решению пользователя файловое `birth time` на NFS не изменяется: стандартного способа задать его в прошлое нет.
- После физического удаления последнего архивного файла удаляются его пустые родительские каталоги. При запуске catalog-service дополнительно удаляются только пустые каталоги внутри `/archive`, снизу вверх; файлы и непустые каталоги не затрагиваются.
- `GET /api/v1/videos/{id}/archive` проверяет глобальную архивную копию независимо от владельца. При её наличии «Архивировать» заменяется на «Скачать из архива», файл сразу скачивается в браузер, а DASH использует архивное качество вместо YouTube. Личная ссылка в библиотеке для этого не требуется и в квоту не добавляется. Автотриггер 30 секунд/5% не создаёт задание, если копия существует у любого пользователя.
- `GET /media/v/{id}/logs?session=...` передаёт строки подготовки воспроизведения через SSE: проверку архива, форматы, MP4-индексы, remux и готовность манифеста, без подписанных URL или секретов. Клиент открывает канал при появлении чёрного фрейма, хранит не более десяти строк, сдвигает их за `0,18 с` и снижает непрозрачность предыдущих на `0,1`. Канал и overlay закрываются при готовности плеера; быстрые анимации автоматически не проверяются.
- Настройка `preferBestQuality=true` хранится в `user_settings` и меняется независимым переключателем. При включении Shaka отключает ABR и выбирает вариант с максимальным разрешением, при равенстве — с максимальным битрейтом; при выключении ABR снова разрешён.

## 33. Журнал подготовки и восстановление после блокировки экрана

- Готовность controls больше не зависит только от завершения асинхронного `player.load()`. События `<video>` и проверка `currentSrc`/`readyState` при `visibilitychange` и `pageshow` не дают показать overlay или заблокировать кнопку, если Android приостановил JavaScript, но само видео уже загружено и продолжает работать. Overlay показывается только до фактической готовности видео.
- Ротация access-token обновляет session, но не считается сменой страницы: эффект загрузки маршрута зависит от `location` и факта аутентификации, а не от объекта session. Поэтому обновление JWT не сбрасывает архивную версию и не перезапускает работающий плеер.
- `usePlaybackLogs` очищает записи только при смене видео или playback-сессии. Остановка SSE после готовности сохраняет последние десять строк и не создаёт повторную серверную сессию с ложным «Ожидание запроса манифеста…».
- Последняя строка журнала — кнопка в той же панели, что и управление воспроизведением и скачивание. Она открывает popup с последними десятью строками; используется тот же `PlaybackLog`, поэтому сдвиг за `0,18 с` и затемнение предыдущих строк совпадают с первоначальным overlay. Крестик и позиционирование — общие с остальными popup.

### Приёмка

- `./gradlew build` и `npm run build --prefix web` проходят. Web развёрнут в Docker; на `TM0qeOHg1oI` проверены воспроизведение архивного DASH без overlay, активная кнопка play/pause, последняя строка «DASH-манифест готов» и popup с пятью фактическими записями подготовки (лимит хранения — десять).

Быстрые анимации по требованию пользователя не проверялись.

## 34. Перемотка двойным кликом и тапом

- Двойной клик по левой половине `<video>` перематывает на 10 секунд назад, по правой — на 10 вперёд. Позиция ограничена диапазоном от нуля до длительности видео. Обработчик работает в capture-фазе на прозрачной `.seek-gestures` над видео, поэтому нативный double-click fullscreen не вызывается.
- Для touch реализовано распознавание двух primary-тапов за `350 мс` на расстоянии до `40px`: используется та же функция перемотки, а следующий нативный `dblclick` подавляется, чтобы не применить смещение дважды. Нижние `48px` плеера исключены из жеста, поэтому системные controls не вызывают перемотку.
- Жест работает только после фактической готовности видео. Одиночный клик по `.seek-gestures` сохраняет стандартное переключение play/pause, а нативные controls внизу остаются доступными. Назначение областей указано в доступном `aria-label` видео.

На остановленном видео финальная реализация перемотала справа `2:53 → 3:03`, затем влево `3:03 → 2:53` без fullscreen и без смены паузы. ## 40. Полный собственный player controls и SponsorBlock на шкале

- `PlayerControls` заменяет нативные controls и старые кнопки качества/театра под видео. Общий фон overlay прозрачный, левая и правая группы — полупрозрачные чёрные pill-панели. Слева: play/pause, mute и громкость, позиция/длительность; справа: постоянная настройка autoplay, единое меню качества/аудиодорожки/субтитров (раздел 55), театр с Ambilight и fullscreen всего `.video-frame` через Fullscreen API.
- Шкала имеет полупрозрачный серый остаток, отдельный буфер и красную просмотренную часть с круглым указателем. Сегменты рисуются поверх них и ограничиваются длительностью видео. Цвета соответствуют [официальному `barTypes` SponsorBlock](https://github.com/ajayyy/SponsorBlock/blob/master/src/config.ts): sponsor `#00d400`, selfpromo `#ffff00`, intro `#00ffff`, outro `#0202ed` и остальные категории с opacity 0,7.
- Выделение внутри `.video-frame` запрещено в CSS, повторный `mousedown` отменяется. Время эффекта перемотки округляется `Math.round`. `pointerup` и `click` используют общий отложенный переключатель controls; повторный click в пределах 500 мс после pointer и двойной жест отменяются, поэтому отложенный mobile click не скрывает только что показанную панель. Двойной клик/тап по-прежнему перематывает на 10 секунд.
- `SponsorBlockClient` передаёт `categories` как шаблонный параметр, а не как заранее закодированную строку: устранено двойное кодирование и ошибка API `400 categories parameter does not match format requirements`. Тест проверяет raw query `videoID=video&categories=%5B%22sponsor%22%5D` и преобразование диапазонов.
- Начальные settings/progress/locations загружаются через `allSettled`: сбой одного запроса не отбрасывает остальные. Shaka ждёт первой загрузки настроек; `autoplayRef` получает значение до запуска, а последующая ротация JWT не перезапускает плеер.

## 47. Устойчивость прогрессивного MP4 и старого кэша

- Для `MQziBPCMEL8` метаданные и `madeForKids=true` приходили, но манифест возвращал `500`: объединённый itag 18 не содержит `indexRange`, поэтому media-service должен скачать начало MP4 и найти `sidx`. В этот момент TLS handshake с googlevideo через SOCKS5 завершался таймаутом. Отдельный сегмент после повторных подключений вернул `206`, `upstream_egress_ok` затем восстановился до `1`; удаление или региональная блокировка ролика не подтверждены.
- `MediaRetry` делает не более двух дополнительных попыток с backoff 1 и 2 секунды при `WebClientRequestException`/`TimeoutException` при чтении MP4-индекса и начале сегмента. HTTP-ответы с ошибками, включая `403/404/429`, не повторяются. Это ограниченная обработка сетевых сбоев, а не скрытие ошибок upstream или смена egress.
- В этом MP4 `moov` имеет размер 141 911 байт, а `sidx` отсутствует: сразу после него идёт `mdat`. Кроме того, Android не прислал codecs, а fallback `avc1.42001E` ошибочно обозначал Baseline, хотя фактический `ffprobe` показал H.264 Main. `Mp4IndexService` извлекает `avc1.4D401E` непосредственно из `avcC`, сохраняя аудиокодек и настоящие init/index ranges.
- Попытка выдать один `mdat` как сегмент привела к Shaka `3014 MEDIA_SOURCE_OPERATION_FAILED`: прогрессивный файл не содержит DASH-фрагментов. Теперь `ProgressiveDashService` перехватывает единственный прогрессивный формат, скачивает его через `youtubeWebClient` и запускает ffmpeg с `-c copy` и DASH-muxer. Возвращаются настоящие init/media `.m4s` через `/media/v/{id}/remux/{filename}`, без перекодирования и искусственных byte-range сегментов.
- Remux-кэш находится в `/tmp/spanktube-dash` и живёт шесть часов, одновременные запросы одного видео используют общую подготовку. `@EnableScheduling` запускает очистку просроченных каталогов раз в час. Пути проверяются на выход за пределы remux-каталога.
- На `MQziBPCMEL8` ffmpeg создал 76 видеофрагментов и 98 аудиофрагментов с `init-0.m4s` и `init-1.m4s`. После этого Shaka перешёл в фактическое состояние «Воспроизведение», кадр отображается, затем ролик поставлен на паузу. Реальное Android-устройство в этой приёмке не использовалось.
- `VideoDetails.madeForKids` имеет nullable-тип `Boolean` для обратной совместимости с уже сохранёнными `streams:v3` Redis-записями без нового поля. Публичный API нормализует отсутствие поля в `false`, поэтому старый кэш не требует инвалидации и не вызывает `MismatchedInputException`.
- `MediaRetryTest` подтверждает две дополнительные попытки при сетевом сбое и одну попытку при HTTP `403`; `KidsVideoParserTest` проверяет чтение старого JSON без `madeForKids`.

## 48. Архивный DASH по запрошенным фрагментам

- Прежний `ArchivePlaybackService.prepare()` запускал ffmpeg на весь MKV и ждал завершения всех сегментов до возврата MPD. Это подтверждённая причина зависания тяжёлых архивов, а не только сетевая задержка.
- `OnDemandDashService` создаёт `ondemand.mpd` по `SegmentTimeline` из ключевых кадров. `MatroskaIndexReader` читает `SeekHead`, смещение `Cues` и `CueTime` без чтения медиапотока. `SeekPosition` имеет ID `0x53AC`; `CueTrackPositions` — контейнер `0xB7`, внутри которого номер видеодорожки находится в `CueTrack=0xF7`. При отсутствии Cues остаётся явно зарегистрированный fallback на `ffprobe`, а не скрытое ожидание полного remux.
- MPD не требует создания видеофрагментов заранее. `init-v/a.m4s` и `gop-v/a-NNNNN.m4s` создаются только при фактическом HTTP-запросе соответствующего сегмента, через `ffmpeg -c copy`; сегменты кэшируются по mtime исходника. Одновременные запросы одного сегмента блокируются на уровне этого файла, разные фрагменты могут готовиться параллельно.
- `setts=pts=PTS+<start-ms>:dts=DTS+<start-ms>` вместе с `frag_discont` и `avoid_negative_ts=disabled` сохраняет абсолютный `baseMediaDecodeTime` каждого GOP в `tfdt`. Простые `-start_at_zero`/`-output_ts_offset` для отдельных файлов обнуляли `tfdt`: Shaka ошибочно сокращал длительность и последовательно запрашивал сотни фрагментов, поэтому такой вариант не применяется.

- Docker-приёмка `80o75wemHb8` (3 088 828 211 байт, 40:32, VP9 2160p + Opus): MPD с 1618 интервалами возвращается примерно за 0,5 с, после него нет заранее созданных GOP. ## 67. Compact-режим MP4-индексов и их кэш

- По модели [LibreTube OnlinePlayerService.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/services/OnlinePlayerService.kt) список форматов получается один раз через `StreamInfo`, а media source создаётся для выбранного воспроизведения, без предварительного чтения всех индексов. В SpankTube `Mp4IndexService` по умолчанию уменьшает дубликаты: одно видео на каждое разрешение с предпочтением MP4 и одно аудио на каждую уникальную подпись `(mimeType, language, label, original, autoGenerated)`. Все разрешения и различающиеся языки/названия/автодорожки остаются, progressive MP4 не объединяется с video-only.
- `full=true` на `/media/v/{id}/manifest.mpd` отключает compact-режим и сохраняет старый список всех кодеков и вариантов. Обычный web-плеер использует compact по умолчанию, поэтому `YcVx5lkmEQk` требует 13 дорожек вместо 28: шесть видео по одному на разрешение и семь различающихся аудио.
- Обогащённые `sidx` и фактический H.264-профиль кэшируются на пять минут в `Mono.cache()`, одновременные MPD одного видео и режима разделяют одно вычисление. Кэш ограничен 128 записями и очищается при ошибке/отмене, поэтому повторный `player.load()` после authenticated prefetch не скачивает заголовки заново. Чтение индексов выполняется шестью параллельными задачами вместо четырёх. Подписанные URL остаются на media-service и используют тот же egress.
- `Mp4IndexServiceTest` проверяет сохранение разрешений, разных языков/автодорожек и progressive MP4, выбор MP4 при равной высоте, кэш повторного запроса и независимость full-режима. WebM-аудио по-прежнему не требует MP4-запроса. Другие пути DASH, архивный on-demand MKV, HLS-only эфир и progressive remux не изменены.

- Приёмка compact на VM: `YcVx5lkmEQk` содержит 6 video и 7 различающихся audio вместо 18+10 в full-режиме. Первый MPD занял `21,328 с`, повторный из кэша `0,047 с`, full-режим `23,078 с` и вернул 28 дорожек. Shaka начал воспроизведение за `18,184 с`. `H3f-Md1FzDw`, `3TYZjVzWazE` и активный HLS-эфир `rFZHOHl-L8A` также воспроизводятся. Полный `./gradlew build` и `git diff --check` проходят.


## 70. Задержка запуска видео и кэш redirect googlevideo

- Замеры `m6ROikrQCKI` до изменений: MPD `0,015 с`, инициализация Shaka `5,143 с`, общая подготовка `26,309 с`. ## 73. Ранняя отдача progressive DASH и общий redirect-кэш

- `ProgressiveDashService` запускает ffmpeg с `-i pipe:0` сразу, сохраняет проверенные 8-МиБ чанки в `source.mp4` и одновременно передаёт их в stdin. При возобновлении уже сохранённый префикс сначала копируется в поток, новые чанки не дублируются. `awaitReady()` проверяет XML-манифест и наличие ненулевых init- и первых аудио-/видеофрагментов; проверки выполняются на `boundedElastic` каждые 50 мс с общим десятиминутным таймаутом. Поэтому для MP4 с `moov` в начале больше не требуется ждать скачивание всего файла; при позднем `moov` сохраняется обычное ожидание полного ввода. Перекодирования и искусственных byte-range сегментов нет.
- Пока ffmpeg пишет фрагменты, MPD имеет `type=dynamic`, а `withPresentationDuration()` добавляет известную длительность видео. Shaka использует режим in-progress, а не бесконечный эфир: воспроизведение начинается с нуля или сохранённой позиции, длительность остаётся конечной. После EOF ffmpeg создаёт обычный `static` MPD. Незавершённый `dynamic` MPD после рестарта не принимается за готовый шестичасовой кэш; поздняя ошибка remux удаляет in-memory preparation, а отмена до готовности закрывает stdin и останавливает процесс. Адаптивные DASH, архивный on-demand DASH и HLS активного эфира этот путь не используют.
- `MediaRedirectCache` перенесён в `egress-starter` и записывает только успешные 2xx-цепочки redirect на разрешённых HTTPS-хостах YouTube/googlevideo. Прямые ответы и посторонние хосты не изменяют запросы и не приводят к ошибкам пробы или remote-DNS теста. TTL 30 минут, предел 256 записей и глубина цепочки четыре сохранены. `MediaController` и progressive-загрузчик используют кэш, а HTTP-ошибки инвалидируют конечный адрес. Подписанные URL в журнал не попадают.
- `ProgressiveDashServiceTest` проверяет ранний ответ до разрешения фонового remux, последующий `static`, повторное использование кэша и восстановление незавершённого MPD после рестарта. `MediaRedirectCacheTest` перенесён в starter. `EgressProbeTest` создаёт пробу без фонового планировщика, чтобы её счётчик запросов и метрика не зависели от автоматического запуска контекста.
- На `MQziBPCMEL8` исходный холодный MPD занимал `28,881 с`; после параллельного remux и общего redirect-кэша — `19,079 с`. Ранний `dynamic` MPD получен за `9,894 с`, init имеет 851 байт, первый видеофрагмент — 324 285 байт. Временная диагностическая страница с тем же Shaka и JWT показала первый кадр через `10,724 с` с позиции `0,0` и длительностью `390,0 с`, затем `dynamic,static`. Запуск с `t=20` также воспроизводится. Архивные копии не удалялись, диагностическая страница после проверки удалена из web-контейнера и с VM.

## 76. Проверки на физическом Android и сравнение с LibreTube

- На Samsung Galaxy S25 Ultra (`SM-S938B`, Android 15) через Wireless Debugging выполнены сопряжение и проверки, ранее недоступные без телефона. Установлен официальный [LibreTube v32.1](https://github.com/libre-tube/LibreTube/releases/tag/v32.1) с SHA-256 `437dbb55540ac573f864938fc3595f69fc13df5d568b237aded9935559fe1353`. SpankTube проверен в Chrome 146, в том числе через adb `uiautomator` и Chrome DevTools Protocol. CDP использовался только для чтения состояния DOM/видео и обычных действий UI, без чтения токенов или браузерного хранилища в отчёты.
- В LibreTube нет собственной настройки SOCKS5. Для одинакового egress телефон временно направлялся через локальный HTTP-CONNECT→SOCKS5 bridge к danted с remote DNS. В логах подтверждены `youtube.com`, `youtubei.googleapis.com`, `googlevideo.com`, SponsorBlock и RYD через этот путь; SpankTube использовал штатный серверный egress. Локальный SpankTube не должен был проходить bridge: после сброса proxy страница снова открылась. Основные proxy-настройки восстановлены в `null`, а оставшиеся legacy-ключи сброшены отдельно по разделу 77; bridge и логи остановлены, DevTools forwarding удалён.
- Для холодных запусков процессы останавливались через `am force-stop`, использовались одинаковые videoId и `t=1s`. `pm clear` больше не применялся: Android асинхронно завершал очистку уже после запуска приложения и убивал новый процесс. Для SpankTube проверялись `performance.timeOrigin`, журнал Shaka и `video.paused`/`readyState`; при блокировке autoplay воспроизведение запускалось нативным Play. Для LibreTube время фиксировалось по первому `PLAYING` в `MediaSessionService` после `BUFFERING`.
