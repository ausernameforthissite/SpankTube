## 9. Архив видео на NFS

- Триггеры архивации: (1) автоматически — событие `watch.progress`, порог «просмотрено» 30 сек или 5% (зафиксировано); (2) вручную — **кнопка «Скачать»** у каждого видео, плейлиста и канала. Сохранение плейлиста/канала ставит пакетную задачу со всеми видео, прогрессом в UI, rate limiting и дедупликацией по `video_id`.
- Очередь персистентная и переживает restart: сначала задачи `ADMIN`, затем `VIEWER`, FIFO внутри роли. Между YouTube-запросами — случайная задержка в настраиваемом диапазоне, ограничение параллелизма и повторные попытки с backoff; повторная постановка того же видео не создаёт дубликат задачи или файла.
- Воркер: yt-dlp `bv*+ba` (максимум качества, с `--proxy` из egress-конфига) + **только созданные людьми субтитры** → mux в **MKV** (`ffmpeg -c copy -c:s srt`). Автогенерированные субтитры не запрашиваются и не передаются пользователю. MKV выбран, т.к. вмещает произвольное число текстовых дорожек. Сегменты SponsorBlock вшиваются главами (chapters). Рядом — `info.json` и превью.
- **Дедупликация**: физический файл один на кластер; `videos(video_id, …)` + связка `user_views(user_id, video_id, …)` определяет владельцев. В квоту каждого владельца входит полный размер файла, независимо от числа остальных владельцев.
- Layout: `/archive/{channel_id}/{video_id}/video.mkv`.
- Квоты по умолчанию через env: `ADMIN` 50 ГиБ, `VIEWER` 10 ГиБ. Администратор может задать персональную квоту любому пользователю через admin API; переопределение важнее значения по роли.
- При достижении 90% квоты перед новой загрузкой удаляются пользовательские ссылки по `last_accessed_at` (LRU) до освобождения требуемого объёма. Активные загрузки и текущее воспроизведение не вытесняются. Если один файл больше квоты, задача отклоняется с понятной ошибкой.
- Ручное и LRU-удаление сначала удаляет только ссылку пользователя и освобождает его квоту. Файл, `info.json`, превью и запись `videos` удаляются физически лишь после исчезновения последней ссылки; у остальных пользователей видео остаётся доступным.
- Библиотека: группировка по каналам, длительность и размер в МБ, сортировка по размеру, скачивание MKV на устройство и ручное удаление. Зритель видит только свои `user_views`; админ — всё, фильтры `?user=`, `?channel=` и их комбинация применяются на сервере.
- Контроль объёма — через метрики квоты/занятого места и виджет в админке (см. раздел 16). Правило «никакой автоочистки» заменено только квотным LRU; других автоматических удалений нет.

- Приоритет `ADMIN`: его задание запустилось при `1/5` выполненных элементов пакета `VIEWER`. Пакет продолжается после задержки между элементами.

- Поиск видео/каналов/плейлистов, локальные превью и YouTube-маршруты. Пагинация: 20 элементов и `nextCursor=20`. Каналы без вкладки `videos` отдают метаданные и аватар через корневую страницу.
- Admin API квот и библиотек; `VIEWER` получает `403` на admin API. OpenAPI генерирует актуальные TypeScript-типы; `kustomize build` успешно собирает манифесты. Kubernetes-приёмка на кластере не выполнялась.

Внешнее ограничение: при массовом получении автосубтитров YouTube отвечает `429 Too Many Requests`, SponsorBlock однажды вернул таймаут TLS handshake. Ограничение не обходится. Воркер делает не более трёх попыток, для `429` использует увеличенную паузу, сохраняет частичные файлы только между попытками, удаляет их после окончательной ошибки и показывает текст ошибки в очереди. Полный MKV с SponsorBlock-главами для `dQw4w9WgXcQ` в этой сессии не получен; это не считается пройденной проверкой. Варианты следующего действия: повтор после снятия rate limit, подключение bgutil PO-token provider, обновление yt-dlp или смена адаптера `UpstreamProvider`.

## 22. Ревизия субтитров, превью, скачиваний и realtime UI

- В архив и пользовательские ответы включаются только субтитры из `subtitles`, созданные людьми. `automatic_captions`, `--write-auto-sub` и массовые автопереводы не используются.
- Превью видео больше не вызывает yt-dlp. По аналогии с LibreTube ([ImageHelper.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/helpers/ImageHelper.kt), [SearchResultsAdapter.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/ui/adapters/SearchResultsAdapter.kt)) изображение загружается напрямую по известному URL и кэшируется. Media-service использует `i.ytimg.com/vi/{id}/hqdefault.jpg` через egress, LRU до 32 МиБ и fallback `hqdefault` → `mqdefault` → `default`; максимальное разрешение — только по запросу `quality=max`.
- «Архивировать» создаёт постоянный MKV в библиотеке с максимальным качеством, SponsorBlock-главами и человеческими субтитрами. «Скачать» выбирает видео/аудио дорожки, необязательные субтитры и SponsorBlock. Видео и комбинированный вариант сохраняются в MKV, audio-only — в MP3.
- Повторная архивация видео, которое уже есть в библиотеке пользователя, возвращает `200` и задание со статусом `completed`, не добавляя работу в очередь и не скачивая файл заново. Переиспользуется завершённая одиночная запись; если её нет, создаётся сразу завершённая запись истории. Web показывает «Видео уже заархивировано». После удаления ссылки из библиотеки повторное сохранение снова допускается.
- Временные файлы находятся в `/archive/.downloads/{jobId}` и удаляются через 24 часа. Они не создают ссылку в библиотеке и не расходуют постоянную квоту. Совпадающий готовый вариант используется повторно; совпадение с постоянным архивом отдаёт его без повторного скачивания и без удаления по TTL.
- Очередь сообщает этапы `METADATA`, `DOWNLOADING_VIDEO`/`DOWNLOADING_AUDIO`, `SUBTITLES`, `SPONSORBLOCK`, `MUXING`, `CHAPTERS`, `FINISHING`, `COMPLETED`/`FAILED`, число завершённых этапов, байты и скорость. `SseEmitter` передаёт события через `GET /api/v1/archive/events`; обновления coalesce за 50 мс, байтовый прогресс ограничен четырьмя обновлениями в секунду, heartbeat — каждые 15 секунд. Web читает SSE через fetch с JWT, без polling и без токена в URL.
- Пользователь видит только свои задания. Чужие задания и их метаданные скрыты; возвращается только количество чужих элементов перед первым его ожидающим заданием. Администратор видит всю очередь.
- Кнопки «Скачать» и «Очередь» разделены на основное действие и раскрытие окна. Есть toast, пятисекундная пульсация очереди из серого в ярко-жёлтый с более тусклым свечением (`0.425 с` за полцикла), два прогресс-бара и закрытие popup крестиком или кликом вне него.
- Библиотека содержит превью, разрешение и кодеки. Имя файла: `<название> [<videoId>] (<разрешение>, <кодек видео>, <кодек аудио>).mkv|.mp3`.
- Персональные `autoplay=true`, `hideTechnicalDetails=false` и `preferBestQuality=true` хранятся в `user-service`. `PATCH /users/me/settings` меняет только переданные поля. Дата публикации выводится локальным `Intl.DateTimeFormat` в часовом поясе клиентского устройства.

## 23. Приёмка ревизии в Docker

- На канале `UC__pB6x64-xQM6lma8lBM6g` первые восемь превью получили `200`; повторные запросы заняли около `120–200 мс`. В браузере карточки отображаются с изображениями, без прежних массовых `404`.
- `PATCH` настроек меняет `autoplay` и `hideTechnicalDetails` независимо; значения сохраняются в PostgreSQL.
- Постоянный архив используется повторно без скачивания. Для старых файлов `ffprobe` восстанавливает корректные разрешение и кодеки в имени файла.
- MP3 скачивается и отдаётся как `audio/mpeg`; повторный запрос того же варианта возвращает тот же `jobId`. SHA-256 файла, полученного браузером, совпал с файлом на NFS.
- SSE показывает этапы, текущий элемент, байты и скорость. Зафиксирован прогресс до `8 566 866 B/s`; heartbeat и обновление очереди после рестарта работают.
- Возраст трёх тестовых MP3 искусственно увеличен до 25 часов: все файлы и ссылки удалены, `stage=EXPIRED`, постоянный MKV сохранён. Обычное расписание очистки восстановлено.
- Новая архивация возвращает `202`, повторная активная — `200` и тот же `jobId`. Повторный `POST /api/v1/videos/3TYZjVzWazE/save` для уже имеющегося в библиотеке видео вернул `200`, существующее задание со статусом `completed` и не создал новую работу; это включает текст «Видео уже заархивировано». В API субтитров нет дорожек `automatic`; архивный `ffmpeg` не получает автогенерированные субтитры.
- В web проверены превью канала, popup очереди, автоматическое скачивание MP3 с осмысленным именем и локальные дата/время публикации.
- Пользователь визуально подтвердил toast поверх содержимого и локальную жёлтую пульсацию очереди. Toast добавляется в `document.body` вне React-дерева с `position: fixed; top: 40px` и удаляется через пять секунд, не сдвигая страницу. SSE обновляет очередь во всех браузерах, но toast и пульсацию вызывает только действие в текущем браузере. Отдельная браузерная проверка нового текста для завершённого архива не проводилась; его условие проверено через API.

## 27. Archive-first и история версий видео

- При открытии `/watch` сначала запрашиваются активная архивная версия и её метаданные: название, описание, публикация, длительность, размер, кодеки, канал, локальные ссылка и аватар канала. Для старых записей описание читается из соседнего `info.json`. Длительность измеряется самим MKV через `ffprobe`, а не берётся из потенциально устаревших полей YouTube; результат кэшируется по пути, размеру и `mtime`.
- YouTube-метаданные загружаются параллельно, но не перезапускают уже созданный плеер. Если длительность активного файла отличается от оригинала хотя бы на секунду, web вызывает `POST /api/v1/videos/{id}/refresh`. Если YouTube недоступен, архивное воспроизведение продолжается без замены версии.
- `REFRESH` скачивает актуальную копию в отдельный каталог `{channel_id}/{video_id}/{jobId}/video.mkv` и после успешной регистрации делает её активной. Предыдущая версия получает `superseded_at`, но остаётся на NFS. При неудачной замене активной остаётся прежняя копия.
- `video_versions` хранит неизменяемые `versionId`, метаданные и пути всех версий; `deleted_at` отделяет физически удалённые файлы от superseded-истории. `GET /archive/versions` возвращает историю с названием, длительностью, размером и кодеками. Выбор версии меняет источник того же плеера через `?version={versionId}`, отдельный DASH-кэш и не закрывает кнопку «История».
- По решению пользователя в квоту входят все не удалённые версии (`deleted_at IS NULL`). LRU удаляет только активную версию и не трогает историю; если после LRU места недостаточно, новая архивация/refresh останавливается с явной ошибкой, старые версии сохраняются.

## 43. Архивация через NewPipe и media-service

- `ArchiveDownloader` — общий интерфейс очереди. `NewPipeDownloader` помечен `@Primary` и заменяет YouTube-скачивание через yt-dlp: `ArchiveWorker` передаёт ему `VideoDownload` с метаданными, форматами, субтитрами и оригинальными главами. `YtDlpDownloader` остаётся только источником локальных helpers для ffmpeg/ffprobe и удаления файлов.
- `MediaClient` скачивает выбранные дорожки через `/media/v/{id}/seg/{itag}` блоками Range по 8 МиБ, объединяет их во временные файлы и сообщает реальные байты/скорость в существующий прогресс очереди. Media-service использует Redis-кэш `streams:v3` NewPipe-ответов на пять часов с учётом egress-режима и тот же `youtubeWebClient`, что и плеер. Ошибки HTTP сохраняют исходное тело, включая `ANTIBOT` и `429`.
- Субтитры скачиваются через `/media/v/{id}/sub/{trackId}` и встраиваются как SRT только в MKV; в MP3 не встраиваются. Оригинальные главы берутся из NewPipe `getStreamSegments`, при пустом списке — из HTML-описания с таймкодами; если extractor не вернул ни глав, ни полного описания, они не выдумываются. SponsorBlock-главы всех архивных категорий объединяются с оригинальными в `chapters.ffmeta`. Пустой `404` SponsorBlock означает отсутствие сегментов, а не ошибку архивации.
- После Range-скачивания ffmpeg только мuxирует локальные файлы: видео/аудио кодеки копируются, MP3 кодируется отдельно. `info.json` создаётся из NewPipe-метаданных с `extractor=NewPipeExtractor` и выбранным `format_id`; превью скачивается через media-service. Только после успешной проверки собранного MKV через `ffprobe` удаляются известные входные `video-track.*`, `audio-track.*`, временные `subtitle-*` и `chapters.ffmeta`; итоговый MKV, `info.json` и превью сохраняются. При ошибке сам загрузчик не удаляет временные компоненты; прежняя очистка неуспешного задания в `ArchiveWorker` не изменяется. Квоты, версии, имя файла, дедупликация и защита активной версии не изменены.
- `MEDIA_SERVICE_URL` добавлен в `application.yml`, Docker Compose и Kubernetes-манифест archive-service. Unit/integration-тесты проверяют Range-запросы и сборку частей, тело upstream-ошибки, ffmpeg без yt-dlp, субтитры/главы/`format_id`, категории SponsorBlock и пустой `404`. Полный `./gradlew build` проходит.

## 45. Карточки YouTube и внутренние плейлисты

- «Видео без плейлиста» получает случайный коллаж 2×2 из четырёх превью своего канала. Порядок выбирается заново при изменении списка, а не при каждом рендере.
- Карточка видео содержит превью с длительностью, название, канал, просмотры и относительную дату. Кнопка `⋮` открывает контекстное меню ровно с тремя действиями: «Добавить в плейлист», «Архивировать» и «Скачать». Только два последних действия создают соответствующие задания.
- Внутренние плейлисты хранятся в `user_playlists` и `user_playlist_items`. `POST /api/v1/library/user-playlists` создаёт плейлист с необязательным начальным видео; `GET` без UUID возвращает только плейлисты владельца, `GET /{id}` разрешён любому аутентифицированному пользователю по ссылке. `POST /{id}/videos` разрешён только владельцу и идемпотентно добавляет видео. Добавление в плейлист не создаёт заданий архивации или скачивания.

- Реальные API-проверки двух временных пользователей подтвердили создание `201` с начальным видео, отсутствие дубликата после двух добавлений `204`, чтение по ссылке `200` другим пользователем, запрет изменения `403`, анонимный `401` и ноль заданий архивации у обоих пользователей.

## 50. Пользовательская автоархивация и языковые дорожки

- `user_settings.auto_archive` по умолчанию `true`, поэтому прежнее поведение сохраняется у существующих пользователей. `WatchProgressHandler` не создаёт автоматическую задачу при `auto_archive=false`; ручная архивация и скачивание остаются доступными. Настройка читается archive-service через внутренний API user-service.
- `StreamFormat`/`UpstreamVideo.Format` передают уникальный `trackId`, язык, подпись, `original` и `autoGenerated`. Для NewPipe оригинал определяется по `AudioTrackType.ORIGINAL`, автодубляж — по `ItagItem.isAutoGenerated()` (`isAutoDubbed`). Повторный itag разных языков больше не выбирает дорожку: media-service использует `trackId`, а исходный `formatId` сохраняется для совместимости старых заданий и `info.json`.
- Выбор архивной аудиодорожки сначала учитывает оригинал, затем человеческие варианты, затем автодубляж и битрейт. `UpstreamClient` пропускает в MKV только неавтоматические субтитры. Автодубляж и автосубтитры доступны для просмотра после оригинальных и человеческих вариантов.
- `DashManifestGenerator` создаёт отдельные AdaptationSet с `lang`, `label` и `Role=main` для оригинала/`dub` для остальных. Это устраняет дублирование `Representation id` и ошибку `3007 WEBM_CUES_ELEMENT_MISSING` на многоязычном видео, не удаляя WebM с действительным Cues-индексом. Shaka получает выбор аудио и субтитров; переключение аудио сохраняет видеокачество, переключение качества — язык.
- `OnDemandDashService` дополнительно читает языки/названия дорожек MKV и список субтитров, но не меняет on-demand механику GOP. Архивный `subtitle-N.vtt` извлекается только при фактическом HTTP-запросе, параллельно с ленивыми init/GOP. Автоматические дорожки в архив не попадают.
- `catalog-service/Dockerfile` запускает процесс от `10001:10001`, совпадающего с владельцем файлов NFS. Это устраняет `Operation not permitted` и HTTP `500` при удалении последней библиотечной ссылки, не затрагивая файлы других владельцев.
- В библиотеке действия MKV/удаления — маленькие векторные иконки. На экранах до 640px они заменяются `⋮` и контекстным меню с пунктами «Скачать MKV» и «Удалить» на основе общего `CardContextMenu`.

## 51. Подтверждение batch-архивации и мобильная громкость

- `POST /api/v1/archive/estimate` собирает все страницы видео плейлиста, все страницы видео канала и все страницы его плейлистов, затем оценивает каждое видео параллельно в пуле из четырёх задач. В список новых байтов не входят уже существующие архивные копии. Дубликаты видео из разных плейлистов удаляются с сохранением порядка.
- `ArchivePreflightService` вычисляет байты по `contentLength` либо по битрейту и длительности выбранных оригинальных дорожек. `ArchiveSpeedService` ведёт in-memory статистику байтов/наносекунд видео и аудио через `LongAdder`, не блокируя сетевые вызовы. Время оценивается как сумма видео/аудио по текущим средним скоростям; при отсутствии истории используется запасной предел 3 МиБ/с на дорожку.
- Batch `/save` требует `estimateId`, действительный 15 минут и привязанный к пользователю, типу и цели. Только после подтверждения `ArchiveEstimateDialog` пользователь попадает в очередь ровно одобренный список. Отмена оценки не создаёт заданий. Одиночное видео не требует предварительной оценки.
- `ArchiveSpeedService` учитывает завершённые треки, `ArchivePreflightService` не делает длинные операции в servlet/event-loop потоке: вычисление выполняется на `boundedElastic`, метаданные отдельных видео — на ограниченном пуле. Повторный cursor и превышение 100 страниц являются явной ошибкой.
- На экранах до 640px ползунок громкости скрыт, громкость выставляется 100%; пользователь регулирует её средствами мобильной ОС.

## 56. Ручная запись активного эфира

- Для активного эфира обычные save/refresh/download остаются запрещены, но пользователь может отдельно записать трансляцию. `POST /api/v1/videos/{id}/recording/start` проверяет `LIVE_STREAM`/`AUDIO_LIVE_STREAM` и выбирает DASH при наличии, иначе HLS. Одна активная запись на пользователя и видео; повторный start возвращает существующую. `GET /recording` возвращает последнюю запись владельца, `/stop` переводит её в `STOPPING`.
- `live_recordings` хранит владельца, статус, метаданные, путь, начало, размер и ошибку. Worker запускает ffmpeg только на URL media-service: никаких прямых обращений к YouTube или к raw `googlevideo` из archive-service. `LiveRecordingManifest` принимает `height` и `bandwidth` фактически активного в Shaka variant на момент нажатия «Начать запись»; при их отсутствии выбирается лучший вариант. Среди вариантов выбранной высоты берётся максимальный bandwidth, аудиодорожка остаётся основной/default. Если выбранное качество больше недоступно, запись завершается с явной ошибкой `Selected video quality is no longer available`, без незаметной подмены. DASH сохраняет только выбранные Representation и преобразует их URL в абсолютные адреса media-service.
- Команда `/stop` посылает `q` в stdin ffmpeg, при необходимости завершает процесс и после выхода проверяет MKV через `ffprobe`. Сохраняются `video.mkv`, `info.json` и превью, затем `video.archived` регистрирует новую версию с `quality=LIVE_RECORDING`. Прогресс обновляется каждые пять секунд, размер всех активных записей проверяется по квоте каждые 15 секунд; превышение останавливает запись с явной причиной. При рестарте сервиса незавершённые записи получают `FAILED`, а не фиктивный `COMPLETED`.
- `LibraryService.filename` для `LIVE_RECORDING` добавляет UTC-время старта в формате `yyyy-MM-dd_HH-mm-ss'Z'`, сохраняя разрешение и кодеки. Физический файл остаётся отдельной версией в каталоге записи; прежние архивные версии не перезаписываются.
- Web показывает «Начать запись» с красным кругом и «Остановить запись»/«Остановка записи…» с квадратом `currentColor`, поэтому значок останова соответствует светлой и тёмной теме. При нажатии передаются высота и bandwidth фактически активного variant Shaka, включая текущий вариант в режиме `auto`. Статус берётся с сервера и обновляется во время записи; после завершения доступна кнопка «Скачать запись». При смене `videoId` внутри SPA и при `pagehide` отправляется `POST /recording/stop` с `keepalive=true`, не блокируя навигацию. `GET /recording` обновляет `last_seen_at`; если heartbeat отсутствует 45 секунд, сервер сам переводит запись в `STOPPING` и завершает её с сохранением результата. Переключение между live и архивной версией того же `videoId` запись не останавливает. Автоархивация и автоматический `/refresh` активного эфира не выполняются.

## 61. Прогресс предварительной оценки архивации

- `POST /api/v1/archive/estimate` принимает необязательный `estimateId`, который web генерирует через `newEstimateId()`: предпочтительно `crypto.randomUUID()`, а при его отсутствии в insecure context — 16 байтов через `crypto.getRandomValues`. Поэтому оценка запускается и по HTTP по локальному IP. Старые клиенты без этого поля работают как прежде. Окончательный `Estimate` и проверка `validate` перед постановкой в очередь не изменены.
- `GET /api/v1/archive/estimate/{estimateId}` доступен только владельцу оценки. In-memory прогресс живёт 15 минут и содержит `COLLECTING`, `ESTIMATING`, `COMPLETED`, `FAILED`, общее и обработанное количество видео, число новых/уже архивных, частичные байты, примерное время и скорость. Атомарные счётчики обновляются по завершении каждого видео, поэтому четырёхпоточная оценка не блокирует HTTP-потоки.
- Web открывает `ArchiveEstimateDialog` сразу после нажатия «Архивировать канал/плейлист». Первоначальный вариант опрашивал статус раз в секунду; в разделе 63 он заменён SSE-событиями и отменой вычисления. После готовности появляется прежнее окно подтверждения с итоговыми байтами и временем. Дополнительных YouTube-запросов кроме самой preflight-оценки нет.
- `ArchivePreflightServiceTest` проверяет частичный прогресс с блокированным видео, завершение и запрет доступа другого пользователя. `ArchivePreflightControllerTest` проверяет owner-status и client `estimateId`. Проверки событий и отмены добавлены в разделе 63.

## 62. Дата последней архивации и новые элементы канала

- `GET /api/v1/archive/channel-status/{channelId}` возвращает `lastArchivedAt`, `newVideoCount`, `newPlaylistCount`. `ArchiveRepository.lastChannelArchive` выбирает `max(coalesce(finished_at, created_at))` последней `CHANNEL`-задачи владельца, включая частичную/неуспешную, поэтому дата сохраняется и после удаления файлов. При отсутствии задачи upstream не вызывается и UI ничего дополнительного не показывает.
- `newVideoCount` считает только публикации позже `lastArchivedAt`, у которых ещё нет глобальной архивной копии. Активный эфир и видео без подтверждённой даты не считаются, записи трансляций учитываются наравне с обычными видео. `PageItems` теперь дополнительно несёт `publishedAts` без изменения старых конструкторов и preflight-оценки.
- `newPlaylistCount` считает плейлисты канала, которых нет в библиотеке пользователя: `LibraryController` отдаёт их ID через `/internal/v1/library/playlist-ids`. YouTube `PlaylistInfo` не содержит дату создания/обновления, поэтому web подписывает именно «Плейлистов вне архива», а не выдумывает дату появления. Под кнопкой «Архивировать канал» выводится локальная дата `lastArchivedAt` мелким шрифтом; счётчики видны только при ненулевых значениях.
- `ArchiveChannelStatusServiceTest` проверяет фильтрацию по дате, исключение активного эфира/неизвестных дат, новые записи трансляций и плейлисты вне библиотеки, а также отсутствие upstream-запросов без предыдущей архивации. `LibraryControllerTest` проверяет выдачу ID архивных плейлистов. Полный `./gradlew build`, OpenAPI TypeScript и production `npm run build --prefix web` проходят.


## 63. SSE-прогресс и отмена предварительной оценки

- `GET /api/v1/archive/estimate/{estimateId}/events` доступен только владельцу. После открытия страницы отправляется событие `page`, после анализа видео — `video`; смена фазы отправляет `progress`, а завершение — `completed`, `failed` или `cancelled`. Все они содержат `ArchiveEstimateProgress`; heartbeat `ping` отправляется каждые 15 секунд, терминальное событие закрывает поток. Первый `progress` позволяет подключиться уже после начала вычисления. Обрыв SSE до терминального события вызывает серверную отмену оценки, поэтому закрытие вкладки не зависит только от DOM-событий; reconnect получает актуальный `CANCELLED` без возобновления работы.
- Прогресс содержит `processedVideoCount`, `discoveredVideoCount`, `pageNumber`, `pageVideoCount`, `remainingOnPage` и `videosPerSecond`. Скорость — число завершённых анализов, делённое на время фазы анализа; сбор страниц в неё не входит. При параллельном анализе страница означает страницу последнего завершённого видео, а остаток вычитается атомарно. Найденное при сборе количество приблизительно: дубликаты между источниками удаляются перед формированием итогового списка.
- Порядок и содержимое итогового списка архивации не изменены: обычные видео канала, записи трансляций и видео всех плейлистов собираются со всех страниц, активный эфир исключается, дубликаты удаляются. Пул остаётся четырёхпоточным; HTTP-запросы прогресса не вызывают повторное обращение к YouTube.
- `DELETE /api/v1/archive/estimate/{estimateId}` переводит активную оценку в `CANCELLED`, прерывает рабочие потоки и предотвращает запуск оставшихся в очереди анализов. С раздела 80 POST сразу возвращает `202` и не ждёт результат; `validate` по-прежнему отклоняет отменённый `estimateId`, поэтому подтвердить архивацию по нему нельзя. Отмена не создаёт и не удаляет задания архивации.
- Web заменяет секундный polling одним SSE-потоком и с раздела 80 открывает его только после успешного `202`, исключая гонку с регистрацией ID. После сетевого обрыва reconnect получает отменённое сервером состояние вместо скрытого продолжения вычисления. Диалог показывает проанализированное и найденное количество, текущую страницу, остаток на ней и скорость анализа. Закрытие диалога вызывает `DELETE`; при SPA-навигации, `beforeunload` и `pagehide` активная оценка также останавливается, при выгрузке страницы — через `fetch(..., { keepalive: true })` с текущим JWT. ID активной серверной оценки не очищается при сетевом обрыве POST: он сохраняется до явного результата или отмены, чтобы обработчик ухода не потерял работу после автоматического abort браузера.
- `ArchivePreflightServiceTest` проверяет события страницы и видео, остаток, положительную скорость, прерывание четырёх активных анализов и пропуск двух оставшихся в очереди. `ArchivePreflightControllerTest` проверяет owner-only SSE, `DELETE`, `204` при отмене и новые поля снимка.

## 93. Общие видео в нескольких плейлистах и удаление по владельцам

- `registerChannelPlaylists` дедуплицирует ID только внутри каждого плейлиста, а не между плейлистами. Первичный ключ `library_playlist_items(user_id, playlist_id, video_id)` допускает одно видео в любом числе оригинальных плейлистов пользователя и независимые членства других пользователей. Новый `ArchiveControllerTest.registersSameVideoInEachOriginalPlaylist` проверяет, что `shared` регистрируется и в `p1`, и в `p2` вместе с их собственными видео.
- Изменение SQL или правил владения не потребовалось: `CatalogRepository.deleteLink` уже удаляет `user_views` только для текущих `(username, videoId)` и все строки этого пользователя в `library_playlist_items` с таким `videoId`, без ограничения одним `playlistId`. Затем отдельно считаются оставшиеся `user_views` видео. Пока есть другой владелец, глобальная запись и физический файл сохраняются; после удаления последней ссылки активная версия получает `deleted_at`, запись `videos` удаляется, а `LibraryService.deleteLinkAndFile` удаляет каталог активной копии. Правила сохранения исторических версий из раздела 27 не изменены.
- `CatalogRepositoryTest.sharedVideoHasIndependentMembershipInEachPlaylistAndUserLibrary` проверяет независимые вставки одного ID в два плейлиста и для двух пользователей. `deleteRemovesAllOwnPlaylistLinksAndFileOnlyAfterLastOwner` проверяет удаление всех собственных playlist links, сохранение глобальной записи при оставшемся владельце и возврат пути только после последней ссылки. `LibraryServiceTest.manualDeleteKeepsSharedFileUntilLastOwner` подтверждает сохранение MKV и `info.json` после первого удаления и удаление каталога после последнего.
- В открытом плейлише `LibraryView` раньше сохранял прежний `playlistItems`, потому что загрузка зависела только от `playlistId`/`scope`. Теперь `App.remove` возвращает `true` только после успешного `DELETE`, даже если последующее обновление сводной библиотеки завершилось ошибкой и было показано пользователю. `LibraryView.removeItem` после этого немедленно удаляет ID из текущего списка; отмена подтверждения или ошибка DELETE список не меняет. Обновлённый `library` убирает видео из всех остальных плейлистов и их счётчиков.
- Реальная API-приёмка на изолированной 16-байтовой архивной fixture с двумя временными владельцами и двумя плейлистами у каждого прошла полный цикл: первый `DELETE` вернул `204`, обе ветви первого владельца стали пустыми, обе ветви второго сохранили видео, его `GET /file` вернул `200` и 16 байт, файл остался на NFS. Временные владельцы, SQL-записи и fixture удалены; существующие библиотеки не затрагивались.
