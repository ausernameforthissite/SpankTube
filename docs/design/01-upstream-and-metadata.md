## 6. Слой доступа к YouTube (upstream)

Три адаптера за единым интерфейсом `UpstreamProvider`, выбор по типу операции, с fallback'ами:

1. **NewPipeExtractor** (Java, in-process) — основной безлогинный провайдер: метаданные, форматы, субтитры, комментарии с пагинацией, поиск, вкладки каналов, плейлисты.
2. **yt-dlp sidecar-демон** (REST-обёртка в поде) — fallback и инструмент архивного скачивания. Рядом контейнер bgutil-pot-provider для PO-токенов (ему тоже нужен выход в Google за BotGuard-скриптом — через тот же egress). Версия yt-dlp обновляется автоматической джобой (еженедельно).
3. **YouTube Data API v3** — только аккаунтные операции от имени привязанного пользователя: `subscriptions.list`, плейлисты, лайки/комментарии.

Разрешённые stream-URL кэшируются в Redis (TTL ~5 ч, ключ `videoId+itag`).

Все адаптеры получают HTTP-клиент от общего egress-модуля (раздел 7) — ни один адаптер не создаёт соединений сам.

## 35. NewPipe-метаданные и быстрые превью

- Аналогично [LibreTube NewPipeMediaServiceRepository.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/api/NewPipeMediaServiceRepository.kt), метаданные видео, поиск, каналы/вкладки и плейлисты извлекаются in-process через NewPipeExtractor (`StreamInfo`, `SearchInfo`, `ChannelInfo`/`ChannelTabInfo`, `PlaylistInfo`). Используется тот же закреплённый fork LibreTube `3e863d7`. `ResilientUpstreamProvider` делает yt-dlp fallback, не скрывая ошибку основного адаптера в журнале; недоступность egress и невалидный ввод не вызывают fallback. Data API v3 не используется.
- NewPipe работает через существующий `youtubeHttpClient` и его SOCKS5/remote DNS, без глобальных JVM proxy-флагов. Блокирующие вызовы extractor остаются на `boundedElastic`; HTTP выполняется Reactor Netty. Для видео больше не требуется отдельный запуск channel-запроса ради аватара. Плейлисты загружаются в `MetadataController` только при выборе их вкладки (раздел 64), а не вместе с каждой страницей видео.
- Вместо числовых offset NewPipe выдаёт continuation-token `np:<base64url JSON>` с URL, id, ids, cookies и телом запроса. Он используется для следующих страниц поиска, видео канала и плейлистов; старые числовые cursor обслуживает fallback yt-dlp. Повреждённые cursor отклоняются как невалидный ввод.
- По аналогии с [LibreTube ImageHelper.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/helpers/ImageHelper.kt), изображения загружаются отдельно от метаданных и кэшируются. URL, уже полученные от extractor/yt-dlp, передаются клиенту только как `/media/image?url=...`; media-service проверяет разрешённые YouTube-хосты. Поэтому превью плейлиста/канала не запускает повторное извлечение метаданных. Старые `/media/channel/{id}/avatar` и `/media/playlist/{id}/thumbnail` остаются fallback.
- Одновременные запросы одного изображения объединяются в один HTTP-вызов, успешный результат сохраняется в LRU. Таймаут варианта — 8 секунд; `404`, `410`, `429`, `5xx` и сетевой таймаут переключают на резервное разрешение. Последняя ошибка не маскируется успешным ответом. Архивный downloader yt-dlp и правила human-only субтитров не изменены.

## 38. Канал, вкладки, метаданные SSE и пагинация

- Заголовок канала — flex-строка: аватар и по центру относительно него название/подписчики слева, «Архивировать канал» справа с тем же внутренним отступом `16px`, что и у аватара слева/сверху. Видео и плейлисты разделены вкладками; ширина `.result-grid` не изменена. Стрелки «История» и «Настройки» имеют тот же размер `0.72rem`, что и у split-кнопок.
- `NewPipePageCodec` хранит continuation-страницы на сервере 30 минут (максимум 512 записей) и возвращает `np:<32 hex>`, поэтому URL не превышает ограничения и `HTTP 414` устранён. Старые длинные base64-токены принимаются для совместимости; неизвестные/просроченные короткие токены отклоняются.
- Канал и плейлист используют `page=<n>` плюс короткий `cursor`. Web запоминает continuation-token для открытых страниц и показывает предыдущую/следующую с векторными SVG-стрелками и до десяти ближайших доступных номеров. Первый номер — 1. Для плейлистов API возвращает `videoCount` и `totalPages` по исходному размеру первой страницы; у канала неизвестный total не выдумывается, доступны последовательные и уже посещённые страницы.
- `GET /api/v1/metadata/logs?session=...` передаёт последние десять строк подготовки метаданных через SSE с heartbeat; записи живут пять минут и доступны даже при подключении после начала извлечения. `logSession` проброшен и через catalog-service для видео. Web открывает SSE сразу при смене страницы, до начала запроса, чтобы не потерять ранние строки; показывает их вместо «Загрузка…» на канале/плейлисте и при подготовке неархивного видео, а для уже архивного видео индикатор загрузки полностью скрыт.

## 46. Отдельный путь для видео «YouTube Детям»

- После ошибки основного NewPipe-провайдера `ResilientUpstreamProvider` вызывает `KidsVideoClient`, который использует `YoutubeStreamHelper.getAndroidReelPlayerResponse` через уже инициализированный NewPipe downloader и тот же SOCKS5-egress. Новый выход в интернет не добавляется.
- Признак детского ролика — машинный `playabilityStatus.miniplayer.miniplayerRenderer.playbackMode=PLAYBACK_MODE_PAUSED_ONLY`, соответствующий ограничению miniplayer для `made for kids`. Локализованный текст не используется. При отсутствии признака выполняется прежний yt-dlp fallback; антибот и недоступность egress не маскируются.
- `KidsVideoParser` принимает только прямые HTTPS stream-URL без HLS и шифрованных `signatureCipher`, поэтому незаполненные/неподдерживаемые ответы не подменяются фиктивными потоками. Публичный API возвращает `madeForKids`. Для известных itag задаются стандартные кодеки, если Android их не прислал. NanoJSON объявлен `compileOnly` той же версии, которая уже присутствует в runtime NewPipe; разбор ответа выполняется существующим Jackson.
- Если доступна только объединённая MP4-дорожка, например itag 18 с видео и аудио, `NewPipeDownloader` принимает её без обязательной отдельной аудиодорожки. Просмотр идёт через обычный DASH media-service, архивация и скачивание — через тот же Range/`MediaClient` и ffmpeg, без yt-dlp в основном пути.
- `KidsVideoParserTest`, `ResilientUpstreamProviderTest` и `NewPipeDownloaderTest` проверяют машинный маркер, отсутствие маркера у обычного ролика, выбор Android вместо yt-dlp, метаданные/субтитры/кодеки и архивацию объединённой дорожки. `ArchiveWorkerTest` отдельно проверяет `quality=18` без `+null` у объединённого формата.

## 64. Производительность каналов, кэш и PO-token provider

- По исходникам [LibreTube NewPipeMediaServiceRepository.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/api/NewPipeMediaServiceRepository.kt) канал и продолжения вкладок загружаются раздельно, а `YoutubeStreamExtractor` получает `PoTokenGenerator`. В SpankTube `GET /api/v1/channels/{id}` больше не запрашивает плейлисты по умолчанию: web передаёт `includePlaylists=true` только для вкладки «Плейлисты». Вкладки видео и трансляций не ждут лишний ответ; повторные страницы видео также не перезагружают плейлисты.
- `MetadataCacheService` хранит метаданные поиска, каналов, вкладок и плейлистов в Redis пять минут с учётом egress-режима и объединяет одновременные cold-запросы одного ключа в один вызов extractor. `VideoService` использует тот же механизм без изменения ключей `spanktube:streams:v3:{mode}:{videoId}` и TTL: пять часов для обычных видео, 30 секунд для активного эфира. Ошибки не кэшируются. Как и [LibreTube ImageHelper.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/helpers/ImageHelper.kt), превью продолжают загружаться отдельно через media-service и не вызывают извлечение метаданных.
- `BgutilPoTokenProvider` реализует NewPipe `PoTokenProvider` для Web client. Он получает visitor data через существующий NewPipe egress-downloader и вызывает внутренний `POST /get_pot` с `content_binding=videoId` и тем же SOCKS5/remote DNS. Возвращаются `visitorData`, `playerRequestPoToken` и `streamingDataPoToken`; Android/embed/iOS остаются без токена, как в LibreTube. HTTP-сервер [bgutil-ytdlp-pot-provider 2.0.2](https://github.com/Brainicism/bgutil-ytdlp-pot-provider) запускается отдельным Docker-контейнером без публичного порта и sidecar-контейнером в Kubernetes. Его исходящий YouTube-трафик идёт через переданный egress, не напрямую.
- yt-dlp получает plugin `bgutil-ytdlp-pot-provider==2.0.2` и `youtubepot-bgutilhttp:base_url` того же HTTP-сервера. PO-токен не гарантирует снятие IP-ограничений YouTube: при сохранении `LOGIN_REQUIRED` или ошибки генератора ошибка и рекомендации показываются пользователю, а не маскируются успешным fallback.
- `ResilientUpstreamProvider` запоминает для каждого NewPipe continuation соответствующий числовой offset yt-dlp по числу уже полученных элементов. Соответствие живёт 30 минут, ограничено 512 записями и привязано к операции и каналу/плейлисту/запросу. При сбое NewPipe на следующей странице yt-dlp больше не получает чужой `np:`-токен и не падает с `Invalid cursor`. Если соответствие неизвестно, пользователю возвращается исходная ошибка NewPipe, а не вторичная ошибка преобразования.
- `ArchivePreflightService` разворачивает runtime-причину `CompletionException` и при параллельном сборе страниц, и при анализе видео. `RestClientResponseException` обрабатывается существующим `ArchiveErrorHandler`, поэтому HTTP-статус и JSON upstream больше не заменяются на `Internal archive error`.
- `MetadataControllerTest` проверяет lazy-загрузку плейлистов, `MetadataCacheServiceTest` — Redis и coalescing, `BgutilPoTokenProviderTest` — visitor data, token, videoId и SOCKS5, `ResilientUpstreamProviderTest` — числовой offset и исходную ошибку при неизвестном cursor, `ArchivePreflightServiceTest` — сохранение downstream-исключения.

- При `ANTIBOT` `ResilientUpstreamProvider` выполняет один дополнительный вызов того же NewPipe-адаптера перед VisionOS/Kids/yt-dlp: проверка Kuplinov показала, что повторный запрос после transient `LOGIN_REQUIRED` успешен. При повторной неудаче цепочка и исходная ошибка остаются видимыми. Прочие причины не повторяются.
- Сбор страниц всех плейлистов канала в preflight выполняется в том же ограниченном пуле, что и другие операции, параллельно между плейлистами. Порядок плейлистов и итоговых videoId сохраняется объединением результатов в исходном порядке; отмена и исключение дубликатов не изменены. `ArchivePreflightServiceTest.collectsChannelPlaylistPagesInParallel` блокирует две страницы одновременно и подтверждает порядок результата.

- После `ApplicationReadyEvent` `BgutilPoTokenProvider` асинхронно получает visitor data и создаёт token minter для тестового videoId. Прогрев не блокирует старт или health-check и не содержит секретов в журнале. Сгенерированный для конкретного videoId токен не подменяет токены других видео: повторно используются только visitor data и minter, поэтому следующие обращения к `/get_pot` не повторяют длительную инициализацию. Ошибка прогрева не скрывается как успешная генерация при последующем реальном запросе.

- На длинном канале обнаружен отдельный предел: Spring MVC завершал ожидание POST-оценки через 30 секунд с `AsyncRequestTimeoutException`, хотя сбор страниц продолжался и позже доходил до анализа видео. `spring.mvc.async.request-timeout` задаётся `ARCHIVE_ASYNC_TIMEOUT_MS` со значением по умолчанию `900000` (15 минут), согласованным с web nginx. Работа остаётся на `boundedElastic` и в ограниченном пуле, поэтому увеличение ожидания ответа не блокирует остальные HTTP-запросы и не заменяет отмену через SSE/DELETE.

- `spring.cloud.gateway.httpclient.response-timeout` по умолчанию `900s`; точный nginx `location = /api/v1/archive/estimate` имеет `proxy_read_timeout 900s`. Это согласует весь путь длинной оценки с `ARCHIVE_ASYNC_TIMEOUT_MS`, не меняя 60-секундный предел остальных API и прежние media-настройки.
- Перед yt-dlp fallback для страниц выполняется один повтор NewPipe после любого не-egress сбоя, включая временный HTML вместо JSON. При повторной неудаче fallback и его настоящая ошибка не скрываются; `IllegalArgumentException` и недоступность egress не повторяются. Тесты подтверждают retry видео/страницы и сохранение преобразования continuation.


## 68. Параллельные метаданные видео

- В `CatalogVideoController` обнаружена последовательная цепочка: сначала YouTube-метаданные, затем SponsorBlock, затем Return YouTube Dislike. Она добавляла к ответу до десяти секунд независимо от compact-режима MPD. Теперь `upstreamClient.video`, `sponsorBlockClient.segments` и `rydClient.dislikes` запускаются одновременно на `boundedElastic` и объединяются через `Mono.zip`, по аналогии с параллельными `respAsync`/`dislikesAsync` в [LibreTube NewPipeMediaServiceRepository.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/api/NewPipeMediaServiceRepository.kt).
- Тип JSON и правила ошибок сохранены: `sponsorBlock` всегда присутствует, `dislikeCountEstimate` добавляется только при непустом RYD-ответе, upstream-исключения продолжают проходить через `CatalogErrorHandler`. `spring.mvc.async.request-timeout` имеет значение `CATALOG_ASYNC_TIMEOUT_MS=120000`, а nginx для `/api/v1/videos/{id}` — `proxy_read_timeout 120s`, поэтому reactive контроллер не получает новый предел 30/60 секунд.
- `CatalogVideoControllerTest` блокирует SponsorBlock и RYD одновременно и подтверждает параллельный старт, сбор JSON и отсутствие повторных вызовов. Compact-режим MPD, архивный DASH и HLS не изменяются.

- Приёмка после распараллеливания метаданных: полная перезагрузка `YcVx5lkmEQk` начала воспроизведение за `9,818 с` вместо ожидания на этапе метаданных. Все 21 ранее проверенные видео и стримы снова воспроизводятся: обычные, Kids/progressive MP4, многоязычные, архивные MKV, записи трансляций и активный HLS-эфир. `wQzNzrJuL6E` ожидаемо требует подтверждения возраста и не считается регрессией. `autoArchive=false` не изменялся, новых заданий архивации не создавалось. Полный `./gradlew build` и `nginx -t` проходят.

- Отдельная проверка RYD и SponsorBlock после распараллеливания: `YcVx5lkmEQk` вернул сегмент `86,183–117,513` и `dislikeCountEstimate=226`, отображаемый как `≈226 дизлайков` и `SponsorBlock (1)`. `vDmjw-c_R2k` вернул уже три актуальных сегмента — `108,33–123,176`, `150,443–324,177`, `1772,232–1831,72` — и `dislikeCountEstimate=1511`, отображаемый как `≈1 511 дизлайков` и `SponsorBlock (3)`. При последующих регрессиях проверять эти поля обязательно, а не только запуск видео.


## 72. Повторная загрузка SponsorBlock после временного сбоя

- Первый запрос `vDmjw-c_R2k` к SponsorBlock завершился `HTTP connect timed out` и дал временный пустой список, хотя повторный запрос вернул три сегмента. `SponsorBlockClient` теперь делает один дополнительный запрос с паузой 250 мс только после `ResourceAccessException` или HTTP `5xx`. HTTP `404` и другие ответы не повторяются; если вторая попытка тоже неуспешна, возвращаются пустой список и warning, без маскировки недоступности сервиса.
- `SponsorBlockClientTest` проверяет успешный ответ после `503` и отсутствие повтора `404`. Повторный `Mono.zip` с YouTube и RYD по-прежнему не блокирует остальные HTTP-запросы. В production `vDmjw-c_R2k` показывает `SponsorBlock (3)` и воспроизводится; RYD возвращается независимо и отображается как оценка.


## 78. TTML-субтитры и оставшиеся проверки на Android

- `YoutubeStreamExtractor.getSubtitlesDefault()` возвращает `MediaFormat.TTML`, а `NewPipeUpstreamProvider` раньше пропускал только `vtt`. Поэтому даже при наличии `captionTracks` в API SpankTube оказывался пустым список субтитров. `subtitleTrack` теперь принимает `vtt` и `ttml`; для TTML меняется только параметр YouTube `fmt=ttml` на `fmt=vtt`. Язык, `trackId` и признак `autoGenerated` сохраняются, неподдерживаемые форматы по-прежнему игнорируются. Для архива по-прежнему выбираются только человеческие дорожки; автоматические доступны только для просмотра.
- `NewPipeSubtitleTracksTest` проверяет преобразование TTML в VTT, сохранение автоматической пометки и пропуск неподдерживаемого формата. Полный `./gradlew build` и `git diff --check` проходят. Изменение не затрагивает медиаформаты или egress.
- `kJQP7kiw5Fk` подтверждает исправление: yt-dlp находит человеческие дорожки, API возвращает шесть (`en`, ещё один `en`, `en-US`, `ja`, `es`, `es-ES`), MPD содержит шесть `AdaptationSet contentType="text"`. `/sub/sub-en-0` возвращает `WEBVTT`, а не TTML или ошибку. На реальном Chrome `English` имеет `mode=showing`, остальные дорожки — `disabled`, на кадре после 31 секунды виден текст `Fonsi!`. После проверки субтитры отключены, чтобы оставить прежнее состояние.
- Дополнительные точные пары с фактическим `PLAYING` у обоих приложений: `5JVXD1w6KYw` — SpankTube `6,928 с`, LibreTube `15,761 с`; `gTGdQ9mfJL4` — SpankTube `6,661 с`, LibreTube `15,105 с`. Нативный Play при блокировке autoplay учитывается отдельно от готовности Shaka. Ошибки тестового скрипта, который повторно искал Play после начала воспроизведения, не считаются временем приложения.
- Upstream progressive `MQziBPCMEL8` на телефоне показал первый кадр за `7,434 с`, длительность `390 с`, типы `dynamic` и затем `static`, ошибки отсутствуют. Отдельный Shaka-инстанс использовал тот же JWT и media-service; архивная копия не удалялась. Обычная страница после удаления диагностики снова воспроизводится.
- При выполнении проверок proxy для LibreTube включается явно через `http_proxy` и `global_http_proxy_host`/`global_http_proxy_port`; перед SpankTube обе группы сбрасываются. После завершения `http_proxy=null`, legacy host пуст, legacy port `0`, DevTools forwarding удалён, временные файлы удалены. Официальный LibreTube остаётся установленным, ошибки `VISIONOS player response is not valid` в отдельных ранее неуспешных прогонах не скрывались и не засчитывались как успешные.
