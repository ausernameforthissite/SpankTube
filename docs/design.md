# SpankTube — дизайн-документ прокси для YouTube

**Дата:** 2026-11-01
**Статус:** v0.6 (этап 2 дополнен вариантами скачивания, realtime-очередью и персональными настройками)

## 1. Цели и область

Самохостируемый прокси для YouTube, разворачиваемый в локальном кластере Kubernetes. Кластер смотрит в сеть с фильтрацией Роскомнадзора («чебурнет»), прямой доступ к YouTube невозможен — весь исходящий YouTube-трафик идёт через **единый настраиваемый SOCKS5-прокси** (существующий danted в локальной сети, проверен на Telegram; резервный режим — VM с VPN-клиентом в роли default gateway). Клиенты (веб и Android) работают исключительно с API прокси и сами к YouTube не обращаются.

Функциональные требования:

- Просмотр видео с полной метаинформацией: дата публикации, описание с таймкодами, лайки/дизлайки, комментарии с таймкодами, сегменты SponsorBlock, созданные людьми субтитры, все варианты качества.
- На странице видео — иконка канала и рабочая внутренняя ссылка на него. Маршруты видео, каналов и плейлистов повторяют YouTube (`/watch?v=`, `/channel/`, `/c/`, `/@`, `/playlist?list=`).
- Поиск видео и каналов на YouTube без Data API v3; результаты поиска, плейлисты и каналы — с превью через media-service.
- Просмотр произвольных каналов и плейлистов, собственных подписок пользователя и персональная главная страница: подписки + гибридные рекомендации (YouTube при привязанном аккаунте, иначе локальные по истории и подпискам).
- Лента новых видео с каналов из подписок и автоматический пропуск рекламных интеграций по сегментам SponsorBlock.
- Архивация просмотренного и ручное скачивание видео/плейлистов/каналов на NFS: максимальное качество, созданные людьми субтитры, один MKV, персистентная очередь со случайными задержками, приоритет `ADMIN` над `VIEWER`, FIFO внутри роли.
- Библиотека просмотренного и скачанного: зритель — только своё, администратор — всё; группировка по каналам, длительность и размер в МБ, сортировка по размеру, скачивание MKV на устройство и ручное удаление.
- Квоты диска: `ADMIN` 50 ГиБ, `VIEWER` 10 ГиБ через env; персональные переопределения администратором; LRU при 90% квоты. Дедупликация файла между пользователями, квота каждого учитывает полный размер файла, физическое удаление только после удаления последней ссылки.
- Две роли: `VIEWER`, `ADMIN`. Обе могут привязать свой YouTube-аккаунт для действий от своего имени.
- Клиенты: браузерный (React) и Android (Kotlin).

## 2. Ключевые риски и ограничения

1. **Антибот-защита YouTube (главный риск).** YouTube требует PO-токены для видеопотоков и субтитров у ряда клиентов; токен привязан к videoId и генерируется на каждое видео. Нужен отдельный генератор токенов (bgutil-pot-provider) и частые обновления yt-dlp.
2. **Подписанные URL googlevideo** живут ~6 часов и привязаны к IP запросившего — клиентам они бесполезны, байты должен проксировать сервер. Следствие: резолв URL и скачивание байтов должны идти через **один и тот же egress** (см. раздел 7).
3. **Фильтрация РКН и подмена DNS.** Прямой выход к YouTube из кластера невозможен; DNS-ответы провайдера для блокируемых доменов недостоверны — резолвинг имён YouTube должен происходить на стороне SOCKS5-прокси или через доверенный DNS (см. раздел 7).
4. **danted — единая точка отказа и узкое место полосы.** Через него пойдёт весь YouTube-трафик, включая видеобайты (≈5 Мбит/с на зрителя 1080p, до ~25 Мбит/с 4K). Резервный режим — VM с VPN.
5. **Дизлайки** официально недоступны с 2021 года: Return YouTube Dislike даёт точные данные только для архива до 12.2021, дальше — экстраполяция. В UI показывать как оценку.
6. **Квота Data API v3** — 10 000 единиц/день на проект; поиск стоит 100 единиц за вызов. API — только для аккаунтных операций, поиск и просмотр — через неофициальные адаптеры.
7. **Привязка личного Google-аккаунта** к автоматизированному клиенту — риск ограничений со стороны Google. Привязка опциональна: просмотр работает анонимно.
8. **ToS YouTube** запрещает скачивание и рестриминг; риск принимает владелец инфраструктуры. Весь «серый» код изолирован в одном сервисе для быстрой замены/починки.

## 5. Сервисы

| Сервис | Ответственность | YouTube-трафик |
|---|---|---|
| gateway | Маршрутизация, валидация JWT, rate limiting, BFF-агрегация экрана «страница видео» | нет |
| user-service | Внутренние пользователи (VIEWER/ADMIN), JWT (access + refresh, ротация), квоты и персональные переопределения, привязка YouTube-аккаунтов | нет (OAuth-колбэк Google — через egress) |
| youtube-upstream-service | Единственная точка выхода в YouTube; метаданные, поиск, каналы/плейлисты, рекомендации через `UpstreamProvider` | да, через egress |
| catalog-service | Нормализованные метаданные видео/каналов, SponsorBlock + RYD, история, библиотека и применение квот/LRU | только через upstream; SponsorBlock/RYD — напрямую (не заблокированы), но под тем же конфигом на случай изменений |
| subscription-service | Подписки пользователя, детект новых видео (WebSub + RSS), лента | RSS/WebSub — через egress |
| media-service | Проксирование googlevideo (Range, DASH-манифесты), превью/аватары, горячий кэш сегментов, отдача архивного с NFS | да, через egress |
| archive-service | Воркеры скачивания: bestvideo+bestaudio+созданные людьми субтитры → MKV на NFS; персистентная очередь с ADMIN-приоритетом и jitter, дедупликация, ACL и admin-выборки | да, через egress |

## 6. Слой доступа к YouTube (upstream)

Три адаптера за единым интерфейсом `UpstreamProvider`, выбор по типу операции, с fallback'ами:

1. **NewPipeExtractor** (Java, in-process) — основной безлогинный провайдер: метаданные, форматы, субтитры, комментарии с пагинацией, поиск, вкладки каналов, плейлисты.
2. **yt-dlp sidecar-демон** (REST-обёртка в поде) — fallback и инструмент архивного скачивания. Рядом контейнер bgutil-pot-provider для PO-токенов (ему тоже нужен выход в Google за BotGuard-скриптом — через тот же egress). Версия yt-dlp обновляется автоматической джобой (еженедельно).
3. **YouTube Data API v3** — только аккаунтные операции от имени привязанного пользователя: `subscriptions.list`, плейлисты, лайки/комментарии.

Разрешённые stream-URL кэшируются в Redis (TTL ~5 ч, ключ `videoId+itag`).

Все адаптеры получают HTTP-клиент от общего egress-модуля (раздел 7) — ни один адаптер не создаёт соединений сам.

## 7. Выход в интернет: единый SOCKS5-egress

### Конфигурация

Одна точка настройки на весь кластер:

```yaml
# ConfigMap spanktube-egress
mode: socks5            # socks5 | direct (direct — резервный режим VPN-VM gateway)
host: 192.168.x.x       # danted в локальной сети
port: 1080
remoteDns: true         # резолвинг имён на стороне прокси (аналог socks5h)
# Secret spanktube-egress (обязателен): username/password — на danted включена авторизация
```

Конфиг читают: youtube-upstream-service, media-service, archive-service, subscription-service (RSS/WebSub), user-service (OAuth-колбэки Google). SponsorBlock и Return YouTube Dislike по умолчанию идут напрямую (не заблокированы), но тоже подчиняются конфигу отдельным флагом `proxyAuxServices: false`.

### Реализация

- Общий автоконфигурационный модуль **`spanktube-egress-starter`** (Spring Boot starter): поднимает отдельный, посвящённый YouTube-трафику HTTP-клиент (Reactor Netty с `proxy(type = SOCKS5)`), инжектируемый в адаптеры. Внутренние соединения — PostgreSQL, Redis, RabbitMQ, межсервисные вызовы — идут напрямую, без прокси.
- **Запрещено** использовать глобальные JVM-флаги `-DsocksProxyHost/-DsocksProxyPort`: они заворачивают в SOCKS вообще все соединения JVM, включая БД и брокер.
- yt-dlp: `--proxy socks5h://[user:pass@]host:1080` (именно `socks5h` — резолвинг на стороне прокси).
- NewPipeExtractor: ему подсовывается тот же egress HTTP-клиент (Downloader-интерфейс NewPipe позволяет подменить транспорт).

### DNS

РКН подменяет DNS-ответы, поэтому имена YouTube нельзя резолвить кластерным/провайдерским DNS. Два рабочих варианта, выбирается конфигом:

1. **Remote DNS через SOCKS5** (`remoteDns: true`) — клиент передаёт прокси неразрешённое имя хоста, резолвит danted со своей стороны. Основной режим; проверить, что egress HTTP-клиент действительно шлёт unresolved hostname (в Netty это зависит от способа создания адреса — покрыть тестом).
2. **Доверенный DNS в кластере** — CoreDNS форвардит зону YouTube/Google на резолвер, ходящий через тот же SOCKS (DoH/DoT), либо на DNS VM с VPN. Запасной вариант, если где-то remote DNS не сработает.

### Консистентность egress IP

Подписанные URL googlevideo привязаны к IP, с которого их запросили. Поэтому резолв stream-URL (upstream) и скачивание байтов (media-service, archive-service) обязаны идти через один и тот же egress. Смешивать «upstream через danted, media напрямую через VPN-VM» нельзя — URL перестанут работать. При смене `mode` кэш разрешённых URL в Redis инвалидируется (ключ включает идентификатор egress-режима).

### Пропускная способность и отказоустойчивость

- Через danted пойдёт весь видеотрафик: ≈5 Мбит/с на зрителя 1080p, до ~25 Мбит/с 4K, плюс архивные скачивания. Следить за NIC/CPU хоста с danted.
- Если danted станет узким местом, конфиг допускает **раздельные прокси**: `egress.api` (метаданные) и `egress.media` (видеобайты) — например, метаданные через danted, а байты через VPN-VM. По умолчанию оба указывают на один SOCKS5.
- Резерв при падении danted: переключение `mode: direct` на VM с VPN (rolling restart затронутых сервисов). Healthcheck ниже даёт алерт для такого переключения.

### Проверка связности

- В upstream-service — периодическая проба `GET https://www.youtube.com/generate_204` через egress, метрика `upstream_egress_ok{mode=...}` + алерт. При недоступности egress сервисы честно отвечают 503 с причиной, а не молча деградируют.
- Smoke-этап в CI/CD и этап 1 прототипа: проверка «видео резолвится и первый сегмент скачан через egress».

## 8. Стриминг медиа

- media-service генерирует **свой DASH-манифест** `/media/v/{videoId}/manifest.mpd` из списка форматов upstream'а: все качества, аудиодорожки, субтитры. URL сегментов указывают на прокси.
- Проброс **Range-заголовков** к googlevideo (перемотка), keep-alive/HTTP2-пул соединений — через egress HTTP-клиент (раздел 7).
- Горячий LRU-кэш сегментов на локальном SSD пода (emptyDir с лимитом): повторный зритель не дёргает YouTube (и не грузит danted).
- Архивное видео стримится с NFS через **ffmpeg remux на лету** (`-c copy`, без перекодирования) в fMP4/DASH — браузеры MKV нативно не играют; ExoPlayer на Android умеет MKV сам.
- **Решение: только DASH**, HLS не делаем (целевые платформы — десктопные браузеры и Android; Safari не в скоупе).
- Оценка нагрузки: 1080p ≈ 5 Мбит/с на зрителя; медиатрафик выносим на отдельный ingress-хост.

## 9. Архив видео на NFS

- Триггеры архивации: (1) автоматически — событие `watch.progress`, порог «просмотрено» 30 сек или 5% (зафиксировано); (2) вручную — **кнопка «Скачать»** у каждого видео, плейлиста и канала. Сохранение плейлиста/канала ставит пакетную задачу со всеми видео, прогрессом в UI, rate limiting и дедупликацией по `video_id`.
- Очередь персистентная и переживает restart: сначала задачи `ADMIN`, затем `VIEWER`, FIFO внутри роли. Между YouTube-запросами — случайная задержка в настраиваемом диапазоне, ограничение параллелизма и повторные попытки с backoff; повторная постановка того же видео не создаёт дубликат задачи или файла.
- Воркер: yt-dlp `bv*+ba` (максимум качества, с `--proxy` из egress-конфига) + **только созданные людьми субтитры** → mux в **MKV** (`ffmpeg -c copy -c:s srt`). Автогенерированные субтитры не запрашиваются и не передаются пользователю. MKV выбран, т.к. вмещает произвольное число текстовых дорожек. Сегменты SponsorBlock вшиваются главами (chapters). Рядом — `info.json` и превью.
- **Дедупликация**: физический файл один на кластер; `videos(video_id, …)` + связка `user_views(user_id, video_id, …)` определяет владельцев. В квоту каждого владельца входит полный размер файла, независимо от числа остальных владельцев.
- Layout: `/archive/{channel_id}/{video_id}/video.mkv`.
- Квоты по умолчанию через env: `ADMIN` 50 ГиБ, `VIEWER` 10 ГиБ. Администратор может задать персональную квоту любому пользователю через admin API; переопределение важнее значения по роли.
- При достижении 90% квоты перед новой загрузкой удаляются пользовательские ссылки по `last_accessed_at` (LRU) до освобождения требуемого объёма. Активные загрузки и текущее воспроизведение не вытесняются. Если один файл больше квоты, задача отклоняется с понятной ошибкой.
- Ручное и LRU-удаление сначала удаляет только ссылку пользователя и освобождает его квоту. Файл, `info.json`, превью и запись `videos` удаляются физически лишь после исчезновения последней ссылки; у остальных пользователей видео остаётся доступным.
- Библиотека: группировка по каналам, длительность и размер в МБ, сортировка по размеру, скачивание MKV на устройство и ручное удаление. Зритель видит только свои `user_views`; админ — всё, фильтры `?user=`, `?channel=` и их комбинация применяются на сервере.
- Контроль объёма — через метрики квоты/занятого места и виджет в админке (см. раздел 16). Правило «никакой автоочистки» заменено только квотным LRU; других автоматических удалений нет.

## 10. Подписки и лента

- При привязке аккаунта: `subscriptions.list(mine=true)` → таблица каналов пользователя (1 единица квоты за страницу из 50).
- Детект новых видео: **WebSub-пуши** (PubSubHubbub-хаб YouTube шлёт webhook при загрузке на канале — входящий трафик, egress не нужен; но подписка/отписка на хабе — исходящий вызов, идёт через egress) — основной механизм; **polling RSS-фидов** каналов раз в час (тоже через egress) — реконсиляция. Оба бесплатны, квоту не тратят.
- Событие `channel.new_video` → лента → бейдж «новое» в клиентах; опционально FCM-пуш в Android.
- Главная страница индивидуальна: список подписок + рекомендации. При привязанном YouTube-аккаунте используются рекомендации YouTube, иначе локальные — по истории просмотров и подпискам; fallback обязателен и не требует аккаунта.

## 11. Аутентификация, роли, привязка YouTube-аккаунта

- Внутренние пользователи: Spring Security, BCrypt, JWT (RSA), access 15 мин + refresh с ротацией. Роли: `ROLE_VIEWER`, `ROLE_ADMIN`. Keycloak сознательно не берём — оверкилл для двух ролей.
- Привязка YouTube: Google OAuth2 authorization code flow, scopes `youtube.readonly` (+ `youtube.force-ssl` для лайков/комментариев). Обмен кода на токены — серверный вызов к Google, идёт через egress. Refresh-токены в БД с envelope-шифрованием (KEK из Kubernetes Secret).
- Альтернатива для yt-dlp-сценариев: загрузка `cookies.txt` через UI, шифрованное хранение.
- Gateway валидирует JWT и прокидывает роль downstream; ACL-проверки дублируются на уровне запросов в archive/catalog.
- `user-service` хранит персональные квоты. Изменять их может только `ADMIN`; archive/catalog получают действующее значение через внутренний API, кэшируя его на короткое время.

## 12. Модель данных (черновик)


## 16. Деплой в Kubernetes

- Хосты: `spanktube.<домен>` (web), `api.spanktube.<домен>`, отдельный `media.spanktube.<домен>` (жирный трафик не конкурирует с API).
- Wildcard-сертификат в namespace: копия через reflector / External Secrets, либо `default-ssl-certificate` на ingress-контроллере.
- **Egress-конфиг**: ConfigMap `spanktube-egress` + Secret `spanktube-egress` (логин/пароль danted), монтируются/env в сервисы с YouTube-трафиком. NetworkPolicy: подам upstream/media/archive/subscription разрешён egress только на `danted_host:1080` и внутрикластерные адреса — страховка от случайного прямого выхода (который всё равно сломан фильтрацией и только засветит DPI).
- NFS: PV + PVC (RWX) на `/archive`; у archive-воркеров RW, у media-service — RO.
- Секреты (Google OAuth client secret, JWT-ключи, куки) — sealed-secrets / External Secrets Operator.
- Масштабирование: HPA для media-service (CPU/полоса), archive-воркеры по длине очереди (KEDA).
- CI/CD: GitHub Actions → локальный registry → Argo CD/Flux.
- Observability: Prometheus + Grafana, Loki; метрики upstream-адаптеров (доля ошибок по провайдерам) — ранний сигнал поломки YouTube-клиентов; метрика `upstream_egress_ok` и задержка egress-пробы — состояние danted; `nfs_storage_bytes{used,free}` — archive-service периодически читает statfs смонтированного архива (источник данных для `/admin/storage`).

## 18. Принятые решения (2026-10-31, дополнено 2026-11-01)

1. **Порог архивации**: автоматически при 30 сек или 5% просмотра; плюс явная кнопка «Скачать» у видео, плейлистов и каналов (пакетная архивация с rate limiting и прогрессом в UI).
2. **Retention и квоты**: кроме ручного удаления разрешён только квотный LRU при 90%. По умолчанию `ADMIN` 50 ГиБ, `VIEWER` 10 ГиБ (env), администратор может переопределить квоту пользователя. Физический файл общий; ссылка и квота каждого пользователя независимы, файл удаляется после последней ссылки.
3. **Стриминг**: только DASH, HLS не делаем.
4. **Аутентификация внутренних пользователей**: свой JWT на Spring Security, без Keycloak.
5. **Брокер**: RabbitMQ для прототипа и первых версий; после стабилизации приложения — пилот Kafka, поэтому событийная шина изолируется за интерфейсом издателя/подписчика.
6. **danted**: авторизация включена — конфиг egress состоит из IP, порта, имени пользователя и пароля (учётные данные в Secret `spanktube-egress`).
7. **Полоса egress**: один SOCKS5 на весь YouTube-трафик + мониторинг задержки и доступности; раздельные `egress.api` / `egress.media` остаются опцией конфигурации на будущее.
8. **Очередь скачивания**: персистентная, `ADMIN` приоритетнее `VIEWER`, FIFO внутри роли, случайные задержки между YouTube-запросами и дедупликация задач/файлов.
9. **Маршруты и превью**: web-маршруты повторяют YouTube, но остаются на SpankTube; аватары и превью проксируются через media-service.
10. **Поиск**: видео и каналы ищем только через неофициальные адаптеры `UpstreamProvider`, Data API v3 не расходуем.
11. **Рекомендации**: при привязанном аккаунте — YouTube, иначе локальные по истории и подпискам; всегда индивидуальны для пользователя.

## 19. Приложение: прикидки ресурсов

- Трафик: ~5 Мбит/с на зрителя 1080p; исходящий к YouTube дедуплицируется горячим кэшем; весь он проходит через хост с danted.
- Хранилище: 1080p ≈ 2–4 ГБ/час контента, 4K ≈ 10–15 ГБ/час — закладываться на NFS соответственно.
- Архивный mux — `ffmpeg -c copy`, CPU почти не ест; remux-on-the-fly при воспроизведении архива — тоже без перекодирования.

## 20. Итоги этапа 1 и правила для следующих этапов

Этап 1 развёрнут и проверен в Docker на тестовой VM: `upstream_egress_ok=1`, метаданные реального видео, DASH-манифест только с URL media-service, `206 Partial Content` для реального googlevideo и воспроизведение play/pause в Shaka. Секреты находятся только в runtime env с правами `600` и исключены из Docker context.

Зафиксированные практические правила:

- Redirect googlevideo выполняется только через тот же egress и только на HTTPS-хосты `youtube.com`/`googlevideo.com` с поддоменами.
- Для MP4 `initRange` и `indexRange` вычисляются по настоящему `sidx` из контейнера. Искусственное разбиение файла на независимые DASH-сегменты запрещено: оно приводит к `MEDIA_SOURCE_OPERATION_FAILED`. Для форматов без индекса допустим только single-file fallback, без выдачи произвольных кусков за полноценные медиасегменты.
- `play()` и native controls доступны только после успешного `player.load()`. Таймауты manifest/streaming настраиваются отдельно (`timeout`, `connectionTimeout`, `stallTimeout`).
- Docker Compose — поддерживаемое окружение для интеграционных проверок; Kubernetes остаётся целевым production-окружением. BuildKit cache используется для Gradle, при подготовленном кэше допускается `GRADLE_EXTRA_ARGS=--offline`.
- Для WebM и архивного remux нельзя повторять искусственное разбиение MP4: нужен корректный индекс/сегментация либо single-file режим.

План и критерии приёмки финального этапа 2:

1. `youtube-upstream-service`: дата публикации, канал и аватар, поиск видео/каналов/плейлистов с пагинацией, метаданные каналов и плейлистов. Data API v3 для поиска не используется.
2. `media-service`: превью и аватары через egress, корректный DASH по `sidx`, отдача архивного MKV на устройство и для воспроизведения.
3. `archive-service`: `bv*+ba` и созданные людьми субтитры, MKV с `ffmpeg -c copy -c:s srt`, главы SponsorBlock, `info.json`, NFS RWX, персистентная очередь с `ADMIN`-приоритетом, FIFO, jitter и rate limiting, дедупликация задач и файлов.
4. `catalog-service` и `user-service`: PostgreSQL, метаданные, SponsorBlock, RYD-оценка, `videos`/`user_views`, действующие квоты и admin-переопределения, серверные ACL и LRU при 90% с удалением физического файла только после последней ссылки.
5. События `watch.progress`, `video.archive.requested`, `video.archived` / `video.archive.failed` — через собственный event-bus. Автотриггер — 30 секунд или 5% просмотра.
6. Web: дата публикации и ссылка на канал, YouTube-маршруты, поиск и превью, автопропуск SponsorBlock, кнопка «Скачать» у всех сущностей, очередь/прогресс, библиотека по каналам с длительностью/размером/сортировкой, скачивание MKV и ручное удаление, admin-выборки и квоты.
7. Приёмка на реальном видео: MKV и `info.json` на NFS; повторное сохранение не создаёт второй файл или задачу; два пользователя делят файл, но каждый учитывает его размер в квоте; ручное/LRU-удаление ссылки не затрагивает другого владельца, последняя ссылка удаляет файл; зритель видит только своё, администратор — всё; архивное видео играется через DASH; ошибки yt-dlp, очереди и NFS видны пользователю.

## 21. Результаты приёмки этапа 2 в Docker (2026-11-01)

Проверено на тестовой VM и реальной NFS-шаре:

- `upstream_egress_ok=1`; метаданные `3TYZjVzWazE`, дата публикации, канал, локальные URL превью и форматов.
- MKV на NFS: Matroska, H.264 + Opus, `320.068` секунды, `9 728 927` байт, `info.json` рядом. Скачанный через API файл побайтово совпал с NFS.
- Shaka Player: успешные play/pause и для YouTube-потока, и для DASH, созданного из архивного MKV через `ffmpeg -c copy`; прежняя ошибка `play() was interrupted` не воспроизводится.
- Автоархивация по `watch.progress` после 30 секунд, durable RabbitMQ exchange/queues и manual ACK, восстановление очереди из PostgreSQL после рестарта archive-service.
- Приоритет `ADMIN`: его задание запустилось при `1/5` выполненных элементов пакета `VIEWER`. Пакет продолжается после задержки между элементами.
- Совместное владение файлом, независимые квоты, ручное удаление только своей ссылки, LRU при 90% и физическое удаление после последней ссылки. Проверка LRU выполнялась с временной квотой `40 000 000` байт на уже существующем файле.
- Поиск видео/каналов/плейлистов, локальные превью и YouTube-маршруты. Пагинация: 20 элементов и `nextCursor=20`. Каналы без вкладки `videos` отдают метаданные и аватар через корневую страницу.
- Admin API квот и библиотек; `VIEWER` получает `403` на admin API. OpenAPI генерирует актуальные TypeScript-типы; `kustomize build` успешно собирает манифесты. Kubernetes-приёмка на кластере не выполнялась.

Внешнее ограничение: при массовом получении автосубтитров YouTube отвечает `429 Too Many Requests`, SponsorBlock однажды вернул таймаут TLS handshake. Ограничение не обходится. Воркер делает не более трёх попыток, для `429` использует увеличенную паузу, сохраняет частичные файлы только между попытками, удаляет их после окончательной ошибки и показывает текст ошибки в очереди. Полный MKV с SponsorBlock-главами для `dQw4w9WgXcQ` в этой сессии не получен; это не считается пройденной проверкой. Варианты следующего действия: повтор после снятия rate limit, подключение bgutil PO-token provider, обновление yt-dlp или смена адаптера `UpstreamProvider`.

## 22. Ревизия субтитров, превью, скачиваний и realtime UI

- В архив и пользовательские ответы включаются только субтитры из `subtitles`, созданные людьми. `automatic_captions`, `--write-auto-sub` и массовые автопереводы не используются.
- Превью видео больше не вызывает yt-dlp. По аналогии с LibreTube ([ImageHelper.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/helpers/ImageHelper.kt), [SearchResultsAdapter.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/ui/adapters/SearchResultsAdapter.kt)) изображение загружается напрямую по известному URL и кэшируется. Media-service использует `i.ytimg.com/vi/{id}/hqdefault.jpg` через egress, LRU до 32 МиБ и fallback `hqdefault` → `mqdefault` → `default`; максимальное разрешение — только по запросу `quality=max`.
- «Архивировать» создаёт постоянный MKV в библиотеке с максимальным качеством, SponsorBlock-главами и человеческими субтитрами. «Скачать» выбирает видео/аудио дорожки, необязательные субтитры и SponsorBlock. Видео и комбинированный вариант сохраняются в MKV, audio-only — в MP3.
- Повторная архивация видео, которое уже есть в библиотеке пользователя, возвращает `200` и задание со статусом `completed`, не добавляя работу в очередь и не скачивая файл заново. Переиспользуется завершённая одиночная запись; если её нет, создаётся сразу завершённая запись истории. Web показывает «Видео уже заархивировано». После удаления ссылки из библиотеки повторное сохранение снова допускается.
- Временные файлы находятся в `/archive/.downloads/{jobId}` и удаляются через 24 часа. Они не создают ссылку в библиотеке и не расходуют постоянную квоту. Совпадающий готовый вариант используется повторно; совпадение с постоянным архивом отдаёт его без повторного скачивания и без удаления по TTL.
- Очередь сообщает этапы `METADATA`, `DOWNLOADING_VIDEO`/`DOWNLOADING_AUDIO`, `SUBTITLES`, `SPONSORBLOCK`, `MUXING`, `CHAPTERS`, `FINISHING`, `COMPLETED`/`FAILED`, число завершённых этапов, байты и скорость. `SseEmitter` передаёт события через `GET /api/v1/archive/events`; обновления coalesce за 50 мс, байтовый прогресс ограничен четырьмя обновлениями в секунду, heartbeat — каждые 15 секунд. Web читает SSE через fetch с JWT, без polling и без токена в URL.
- Пользователь видит только свои задания. Чужие задания и их метаданные скрыты; возвращается только количество чужих элементов перед первым его ожидающим заданием. Администратор видит всю очередь.
- Кнопки «Скачать» и «Очередь» разделены на основное действие и раскрытие окна. Есть toast, пятисекундная пульсация очереди из серого в ярко-жёлтый с более тусклым свечением (`0.425 с` за полцикла), два прогресс-бара и закрытие popup крестиком или кликом вне него.
- Библиотека содержит превью, разрешение и кодеки. Имя файла: `<название> [<videoId>] (<разрешение>, <кодек видео>, <кодек аудио>).mkv|.mp3`.
- Персональные `autoplay=true`, `hideTechnicalDetails=false` и `preferBestQuality=true` хранятся в `user-service`. `PATCH /users/me/settings` меняет только переданные поля. Дата публикации выводится локальным `Intl.DateTimeFormat` в часовом поясе клиентского устройства.

## 23. Приёмка ревизии в Docker

- На канале `UC__pB6x64-xQM6lma8lBM6g` первые восемь превью получили `200`; повторные запросы заняли около `120–200 мс`. В браузере карточки отображаются с изображениями, без прежних массовых `404`.
- `PATCH` настроек меняет `autoplay` и `hideTechnicalDetails` независимо; значения сохраняются в PostgreSQL.
- Постоянный архив используется повторно без скачивания. Для старых файлов `ffprobe` восстанавливает корректные разрешение и кодеки в имени файла.
- MP3 скачивается и отдаётся как `audio/mpeg`; повторный запрос того же варианта возвращает тот же `jobId`. SHA-256 файла, полученного браузером, совпал с файлом на NFS.
- SSE показывает этапы, текущий элемент, байты и скорость. Зафиксирован прогресс до `8 566 866 B/s`; heartbeat и обновление очереди после рестарта работают.

## 24. Ревизия очереди, общего архива и загрузки плеера

- Неуспешные задания скрываются через час после `finished_at`. Любое терминальное задание можно скрыть через `DELETE /api/v1/archive/jobs/{jobId}`; `archive_job_dismissals` делает скрытие персональным и не удаляет историю или файл. Активное задание скрыть нельзя.
- `archive_jobs.updated_at` обновляется запросами репозитория при каждом изменении состояния или прогресса. Web показывает локальное время, а для другого дня — дату и время. Название ведёт на `/watch?v=...` внутри SpankTube; переход из popup не закрывает его. Список в popup получает отступ под крестиком.
- Одиночное задание считает элементами этапы `METADATA`, `DOWNLOADING_VIDEO`, `DOWNLOADING_AUDIO`, `SUBTITLES`, `SPONSORBLOCK`, `MUXING`, `CHAPTERS`, `FINISHING`; отключённые опцией этапы не входят в `totalCount`. Байтовый прогресс относится к текущей дорожке и скрывается в терминальном состоянии. Разрешение, кодеки и размер остаются видны после завершения. Плейлисты и каналы разворачиваются в отдельные `VIDEO`-задания.
- Завершающий MKV-remux сохраняет главы SponsorBlock. Для архивных и временных файлов применяется `yt-dlp --mtime`; после ffmpeg файловая дата изменения восстанавливается по `publishedAt`, а в поддерживаемые контейнеры записывается `creation_time`. По решению пользователя файловое `birth time` на NFS не изменяется: стандартного способа задать его в прошлое нет.
- После физического удаления последнего архивного файла удаляются его пустые родительские каталоги. При запуске catalog-service дополнительно удаляются только пустые каталоги внутри `/archive`, снизу вверх; файлы и непустые каталоги не затрагиваются.
- `GET /api/v1/videos/{id}/archive` проверяет глобальную архивную копию независимо от владельца. При её наличии «Архивировать» заменяется на «Скачать из архива», файл сразу скачивается в браузер, а DASH использует архивное качество вместо YouTube. Личная ссылка в библиотеке для этого не требуется и в квоту не добавляется. Автотриггер 30 секунд/5% не создаёт задание, если копия существует у любого пользователя.
- `GET /media/v/{id}/logs?session=...` передаёт строки подготовки воспроизведения через SSE: проверку архива, форматы, MP4-индексы, remux и готовность манифеста, без подписанных URL или секретов. Клиент открывает канал при появлении чёрного фрейма, хранит не более десяти строк, сдвигает их за `0,18 с` и снижает непрозрачность предыдущих на `0,1`. Канал и overlay закрываются при готовности плеера; быстрые анимации автоматически не проверяются.
- Настройка `preferBestQuality=true` хранится в `user_settings` и меняется независимым переключателем. При включении Shaka отключает ABR и выбирает вариант с максимальным разрешением, при равенстве — с максимальным битрейтом; при выключении ABR снова разрешён.

## 27. Archive-first и история версий видео

- При открытии `/watch` сначала запрашиваются активная архивная версия и её метаданные: название, описание, публикация, длительность, размер, кодеки, канал, локальные ссылка и аватар канала. Для старых записей описание читается из соседнего `info.json`. Длительность измеряется самим MKV через `ffprobe`, а не берётся из потенциально устаревших полей YouTube; результат кэшируется по пути, размеру и `mtime`.
- YouTube-метаданные загружаются параллельно, но не перезапускают уже созданный плеер. Если длительность активного файла отличается от оригинала хотя бы на секунду, web вызывает `POST /api/v1/videos/{id}/refresh`. Если YouTube недоступен, архивное воспроизведение продолжается без замены версии.
- `REFRESH` скачивает актуальную копию в отдельный каталог `{channel_id}/{video_id}/{jobId}/video.mkv` и после успешной регистрации делает её активной. Предыдущая версия получает `superseded_at`, но остаётся на NFS. При неудачной замене активной остаётся прежняя копия.
- `video_versions` хранит неизменяемые `versionId`, метаданные и пути всех версий; `deleted_at` отделяет физически удалённые файлы от superseded-истории. `GET /archive/versions` возвращает историю с названием, длительностью, размером и кодеками. Выбор версии меняет источник того же плеера через `?version={versionId}`, отдельный DASH-кэш и не закрывает кнопку «История».
- По решению пользователя в квоту входят все не удалённые версии (`deleted_at IS NULL`). LRU удаляет только активную версию и не трогает историю; если после LRU места недостаточно, новая архивация/refresh останавливается с явной ошибкой, старые версии сохраняются.

## 35. NewPipe-метаданные и быстрые превью

- Аналогично [LibreTube NewPipeMediaServiceRepository.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/api/NewPipeMediaServiceRepository.kt), метаданные видео, поиск, каналы/вкладки и плейлисты извлекаются in-process через NewPipeExtractor (`StreamInfo`, `SearchInfo`, `ChannelInfo`/`ChannelTabInfo`, `PlaylistInfo`). Используется тот же закреплённый fork LibreTube `3e863d7`. `ResilientUpstreamProvider` делает yt-dlp fallback, не скрывая ошибку основного адаптера в журнале; недоступность egress и невалидный ввод не вызывают fallback. Data API v3 не используется.
- NewPipe работает через существующий `youtubeHttpClient` и его SOCKS5/remote DNS, без глобальных JVM proxy-флагов. Блокирующие вызовы extractor остаются на `boundedElastic`; HTTP выполняется Reactor Netty. Для видео больше не требуется отдельный запуск channel-запроса ради аватара. Канал и его плейлисты загружаются параллельно в `MetadataController`.
- Вместо числовых offset NewPipe выдаёт continuation-token `np:<base64url JSON>` с URL, id, ids, cookies и телом запроса. Он используется для следующих страниц поиска, видео канала и плейлистов; старые числовые cursor обслуживает fallback yt-dlp. Повреждённые cursor отклоняются как невалидный ввод.
- По аналогии с [LibreTube ImageHelper.kt](https://raw.githubusercontent.com/libre-tube/LibreTube/master/app/src/main/java/com/github/libretube/helpers/ImageHelper.kt), изображения загружаются отдельно от метаданных и кэшируются. URL, уже полученные от extractor/yt-dlp, передаются клиенту только как `/media/image?url=...`; media-service проверяет разрешённые YouTube-хосты. Поэтому превью плейлиста/канала не запускает повторное извлечение метаданных. Старые `/media/channel/{id}/avatar` и `/media/playlist/{id}/thumbnail` остаются fallback.
- Одновременные запросы одного изображения объединяются в один HTTP-вызов, успешный результат сохраняется в LRU. Таймаут варианта — 8 секунд; `404`, `410`, `429`, `5xx` и сетевой таймаут переключают на резервное разрешение. Последняя ошибка не маскируется успешным ответом. Архивный downloader yt-dlp и правила human-only субтитров не изменены.

## 36. Таймкоды в URL видео

- `/watch?v=<ID>&t=<seconds>s`, `t=<minutes>m<seconds>s` и `t=<hours>h<minutes>m<seconds>s` разбираются в неотрицательное число секунд с проверкой safe integer. Комбинации с нулевыми компонентами поддерживаются; минуты и секунды могут превышать 59 и нормализуются арифметически.
- После `player.load()` валидный таймкод меньше длительности применяется до `play()` и имеет приоритет над сохранённым прогрессом. Нулевая позиция тоже действительна. Невалидный таймкод или точка вне видео игнорируется, после чего работает обычное возобновление. Настройка autoplay сохраняет своё действие.
- Изменение `t` создаёт новую playback-сессию и перезапускает подготовку плеера даже при неизменном videoId, поэтому переход между таймкодами в SPA работает без полной перезагрузки.

### Приёмка

- `npm run build --prefix web` проходит, web развёрнут в Docker. С отключённым autoplay `t=75s`, `t=1m15s` и `t=0h1m15s` установили `TM0qeOHg1oI` на отображаемые `1:14` (75 секунд с точностью отображения/позиции кадра) вместо сохранённой позиции.

## 38. Канал, вкладки, метаданные SSE и пагинация

- Заголовок канала — flex-строка: аватар и по центру относительно него название/подписчики слева, «Архивировать канал» справа с тем же внутренним отступом `16px`, что и у аватара слева/сверху. Web открывает SSE сразу при смене страницы, до начала запроса, чтобы не потерять ранние строки; показывает их вместо «Загрузка…» на канале/плейлисте и при подготовке неархивного видео, а для уже архивного видео индикатор загрузки полностью скрыт.

## 39. Плеер, иерархическая библиотека и персонализация

### Плеер и карточки

- Одиночный клик/тап по рабочему видео показывает собственные controls и не переключает play/pause; кнопка панели по-прежнему управляет воспроизведением. ### Плейлист, очередь и навигация

- Кнопка «Архивировать» находится в строке названия плейлиста. «Назад» возвращает на вкладку плейлистов канала с сохранённым номером страницы через `from`; при прямом открытии — на первую страницу плейлистов канала владельца.
- Успешные задания скрывают прогресс по элементам. `DELETE /api/v1/archive/jobs` скрывает все видимые завершённые задания пользователя; удаление одного или массовая очистка также удаляют соответствующий временный каталог `.downloads/{jobId}`, не затрагивая постоянный архив.
- Внутренние ссылки и кнопки с `data-nav-url` поддерживают открытие в фоновой вкладке средней кнопкой мыши. Счётчик общего поиска показывает число элементов после дедупликации.

### Библиотека

- Библиотека имеет иерархию канал → плейлисты и видео без плейлиста → элементы плейлиста. Для администратора доступны `scope=own` и `scope=all`; обычный пользователь получает только собственный архив. Для значков архива используется `scope=global` без выдачи чужих владельцев.
- Метаданные сохранённых плейлистов хранятся в `library_playlists`, их элементы — в `library_playlist_items`. Одно видео может находиться в канале автора отдельно и в канале владельца плейлиста; обе позиции ссылаются на один глобальный файл и те же версии. Удаление архивной копии по существующим ACL убирает видео из обеих ветвей.
- Значок архива на карточке открывает `/library?scope=global&channel=...&playlist=...&video=...`. Переходы вверх сохраняют выбранную вкладку и позицию иерархии. На главной показываются рекомендации из собственного архива; внутренние подписки остаются этапом 3.

По умолчанию web локально генерирует SVG-мордочки животных в chibi-стиле, а не обращается к внешнему сервису и не утверждает нейросетевую генерацию.

## 43. Архивация через NewPipe и media-service

- `ArchiveDownloader` — общий интерфейс очереди. `NewPipeDownloader` помечен `@Primary` и заменяет YouTube-скачивание через yt-dlp: `ArchiveWorker` передаёт ему `VideoDownload` с метаданными, форматами, субтитрами и оригинальными главами. `YtDlpDownloader` остаётся только источником локальных helpers для ffmpeg/ffprobe и удаления файлов.
- `MediaClient` скачивает выбранные дорожки через `/media/v/{id}/seg/{itag}` блоками Range по 8 МиБ, объединяет их во временные файлы и сообщает реальные байты/скорость в существующий прогресс очереди. Media-service использует Redis-кэш `streams:v3` NewPipe-ответов на пять часов с учётом egress-режима и тот же `youtubeWebClient`, что и плеер. Ошибки HTTP сохраняют исходное тело, включая `ANTIBOT` и `429`.
- Субтитры скачиваются через `/media/v/{id}/sub/{trackId}` и встраиваются как SRT только в MKV; в MP3 не встраиваются. Оригинальные главы берутся из NewPipe `getStreamSegments`, при пустом списке — из HTML-описания с таймкодами; если extractor не вернул ни глав, ни полного описания, они не выдумываются. SponsorBlock-главы всех архивных категорий объединяются с оригинальными в `chapters.ffmeta`. Пустой `404` SponsorBlock означает отсутствие сегментов, а не ошибку архивации.
- После Range-скачивания ffmpeg только мuxирует локальные файлы: видео/аудио кодеки копируются, MP3 кодируется отдельно. `info.json` создаётся из NewPipe-метаданных с `extractor=NewPipeExtractor` и выбранным `format_id`; превью скачивается через media-service. Квоты, версии, имя файла, дедупликация и защита активной версии не изменены.
- `MEDIA_SERVICE_URL` добавлен в `application.yml`, Docker Compose и Kubernetes-манифест archive-service. Unit/integration-тесты проверяют Range-запросы и сборку частей, тело upstream-ошибки, ffmpeg без yt-dlp, субтитры/главы/`format_id`, категории SponsorBlock и пустой `404`. Полный `./gradlew build` проходит.

## 47. Устойчивость прогрессивного MP4 и старого кэша

- Для `MQziBPCMEL8` метаданные и `madeForKids=true` приходили, но манифест возвращал `500`: объединённый itag 18 не содержит `indexRange`, поэтому media-service должен скачать начало MP4 и найти `sidx`. В этот момент TLS handshake с googlevideo через SOCKS5 завершался таймаутом. Отдельный сегмент после повторных подключений вернул `206`, `upstream_egress_ok` затем восстановился до `1`; удаление или региональная блокировка ролика не подтверждены.
- `MediaRetry` делает не более двух дополнительных попыток с backoff 1 и 2 секунды при `WebClientRequestException`/`TimeoutException` при чтении MP4-индекса и начале сегмента. HTTP-ответы с ошибками, включая `403/404/429`, не повторяются. Это ограниченная обработка сетевых сбоев, а не скрытие ошибок upstream или смена egress.
- В этом MP4 `moov` имеет размер 141 911 байт, а `sidx` отсутствует: сразу после него идёт `mdat`. Кроме того, Android не прислал codecs, а fallback `avc1.42001E` ошибочно обозначал Baseline, хотя фактический `ffprobe` показал H.264 Main. `Mp4IndexService` извлекает `avc1.4D401E` непосредственно из `avcC`, сохраняя аудиокодек и настоящие init/index ranges.
- Попытка выдать один `mdat` как сегмент привела к Shaka `3014 MEDIA_SOURCE_OPERATION_FAILED`: прогрессивный файл не содержит DASH-фрагментов. Теперь `ProgressiveDashService` перехватывает единственный прогрессивный формат, скачивает его через `youtubeWebClient` и запускает ffmpeg с `-c copy` и DASH-muxer. Возвращаются настоящие init/media `.m4s` через `/media/v/{id}/remux/{filename}`, без перекодирования и искусственных byte-range сегментов.
- Remux-кэш находится в `/tmp/spanktube-dash` и живёт шесть часов, одновременные запросы одного видео используют общую подготовку. `@EnableScheduling` запускает очистку просроченных каталогов раз в час. Пути проверяются на выход за пределы remux-каталога.
- На `MQziBPCMEL8` ffmpeg создал 76 видеофрагментов и 98 аудиофрагментов с `init-0.m4s` и `init-1.m4s`. После этого Shaka перешёл в фактическое состояние «Воспроизведение», кадр отображается, затем ролик поставлен на паузу. Реальное Android-устройство в этой приёмке не использовалось.
- `VideoDetails.madeForKids` имеет nullable-тип `Boolean` для обратной совместимости с уже сохранёнными `streams:v3` Redis-записями без нового поля. Публичный API нормализует отсутствие поля в `false`, поэтому старый кэш не требует инвалидации и не вызывает `MismatchedInputException`.
- `MediaRetryTest` подтверждает две дополнительные попытки при сетевом сбое и одну попытку при HTTP `403`; `KidsVideoParserTest` проверяет чтение старого JSON без `madeForKids`.

## 48. Архивный DASH по запрошенным фрагментам

- Прежний `ArchivePlaybackService.prepare()` запускал ffmpeg на весь MKV и ждал завершения всех сегментов до возврата MPD. Это подтверждённая причина зависания тяжёлых архивов, а не только сетевая задержка.
- `OnDemandDashService` создаёт `ondemand.mpd` по `SegmentTimeline` из ключевых кадров. `MatroskaIndexReader` читает `SeekHead`, смещение `Cues` и `CueTime` без чтения медиапотока. `SeekPosition` имеет ID `0x53AC`; `CueTrackPositions` — контейнер `0xB7`, внутри которого номер видеодорожки находится в `CueTrack=0xF7`. При отсутствии Cues остаётся явно зарегистрированный fallback на `ffprobe`, а не скрытое ожидание полного remux.
- MPD не требует создания видеофрагментов заранее. `init-v/a.m4s` и `gop-v/a-NNNNN.m4s` создаются только при фактическом HTTP-запросе соответствующего сегмента, через `ffmpeg -c copy`; сегменты кэшируются по mtime исходника. Одновременные запросы одного сегмента блокируются на уровне этого файла, разные фрагменты могут готовиться параллельно.
- `setts=pts=PTS+<start-ms>:dts=DTS+<start-ms>` вместе с `frag_discont` и `avoid_negative_ts=disabled` сохраняет абсолютный `baseMediaDecodeTime` каждого GOP в `tfdt`. Простые `-start_at_zero`/`-output_ts_offset` для отдельных файлов обнуляли `tfdt`: Shaka ошибочно сокращал длительность и последовательно запрашивал сотни фрагментов, поэтому такой вариант не применяется.
- `MatroskaIndexReaderTest` проверяет EBML/`SeekHead`/`Cues`, включая вложенный `CueTrack`, на маленьком файле без медиапотока. `OnDemandDashServiceTest` подтверждает, что после MPD создаются только запрошенные init/GOP, повторный запрос идёт из кэша; MPD разбирается XML-парсером, а аргументы смещения `tfdt` проверяются отдельно. Чтение stdout процессов асинхронное, чтобы большой список ключевых кадров не блокировал pipe.
- Docker-приёмка `80o75wemHb8` (3 088 828 211 байт, 40:32, VP9 2160p + Opus): MPD с 1618 интервалами возвращается примерно за 0,5 с, после него нет заранее созданных GOP. Init и первые аудио-/видеофрагменты возвращают `200`; второй GOP, созданный сервисом, имеет `tfdt=3737` для видео и `179568` для аудио с timescale 48000. В Shaka подтверждено фактическое воспроизведение до `3:50 / 40:32` и последующая пауза; к этому моменту запрошены только 93 GOP, а не весь ролик. Реальное Android-устройство в этой приёмке не использовалось. Тестовые пользователь, инвайт и запись истории удалены, данные `viewer` и архивный MKV сохранены.

## 49. Восстановление прогрессивного MP4 и архивации после сбоев egress

- `EgressProbe` выполняет не более двух повторов с backoff 1/2 секунды при сетевом сбое или обрыве соединения. Одиночный таймаут `generate_204` больше не должен мгновенно переводить последующие Range-запросы в `503`; `upstream_egress_ok=0` устанавливается после исчерпания повторов. HTTP-ошибки самой пробы не повторяются.
- `ProgressiveDashService` скачивает источник чанками по 8 МиБ с `Range`, начиная с размера уже существующего `source.mp4`. Перед каждой попыткой незавершённый чанк обрезается до его начального смещения, а запись ведётся через `FileChannel.position(offset)` на `boundedElastic`, без платформенно зависимого `APPEND` в asynchronous channel. Размер тела сверяется с `Content-Length`; попытка ограничена двумя минутами, сетевые обрывы получают не более двух повторов. HTTP `403/404/429` не повторяются. Вывод ffmpeg читается асинхронно.
- Web для одиночной совмещённой MP4-дорожки ждёт подготовку MPD authenticated fetch с внешним пределом 15 минут и видимым журналом, затем вызывает `player.load()` на уже готовом кэше. Это исключает `Shaka Error 1003` на двухминутном таймауте манифеста во время длинной подготовки. Обычные адаптивные форматы и архивный `OnDemandDashService` по этому пути не изменены.
- `MediaClient` архивации повторяет только текущий чанк при сетевом обрыве и ответах `502/503/504`, максимум два повтора с backoff 1/2 секунды. Уже завершённые диапазоны не скачиваются заново, частичные байты неудавшегося чанка отбрасываются, фактический размер сверяется с `Content-Length`. Прочие ошибки и тела upstream-ошибок не маскируются.
- `EgressProbeTest` проверяет восстановление пробы после обрыва; `ProgressiveDashServiceTest` — продолжение частичного MP4 и повтор прерванного тела без дублирования байтов на Windows и Linux; `MediaClientTest` — повтор `503` и обрезание частичного чанка. Архивный DASH из раздела 48 не изменялся и проверяется отдельно.
- В web nginx для `GET /media/v/{id}/manifest.mpd` задан `proxy_read_timeout=900s`: прежний предел 60 секунд обрывал первую длительную подготовку с `504` ещё до готовности MPD. Он согласован с внешним пределом prefetch, а не заменяет собой таймауты чанков и повторы backend.
- Docker-приёмка `h07SpmhcWUE`: частичный `source.mp4` продолжен с `336852480` до `518013910` байт, MPD создан, Shaka перешёл в фактическое состояние «Воспроизведение» и запросил последовательные DASH-фрагменты. `MQziBPCMEL8` также воспроизводится в том же сеансе. Архивная задача завершилась со статусом `COMPLETED`; MKV имеет размер `519598747` байт, длительность `8339,609` с, дорожки H.264 и AAC. Повторная проверка `80o75wemHb8` подтвердила фактическое воспроизведение большого архивного MKV и паузу.
